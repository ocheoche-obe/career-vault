Background

Slice 6a built an agent that writes résumés. It worked — six phases of Bedrock calls, a real PDF in S3, a trace row in DynamoDB. But nobody could use it, because the only way to start a run was to hand-craft a JSON event and invoke a Lambda from a terminal. Slice 6b is the slice that turns that machine into a button.

That sounds like pure frontend work. It mostly wasn't, and the reason why is the most useful thing in this page.

Skippable background: the four AWS pieces in play

If you already know what a presigned URL is, jump to the next heading.

S3 is object storage: you put bytes at a key like resumes/<user_id>/<run_id>/resume.pdf and read them back. CareerVault's data bucket is fully private — no public access, ever. So how does a browser display a PDF that lives in a private bucket?

A presigned URL is the answer. The backend, which holds real IAM credentials, computes a signature over "a GET, for this exact key, in this exact bucket, expiring in one hour" and appends it to the URL as query parameters. Anyone holding that URL can perform that one operation until it expires. It is a capability token minted from IAM permissions the browser never sees. Azure calls the same idea a SAS token; GCP calls it a signed URL.

CORS (Cross-Origin Resource Sharing) is a browser rule, not a server rule. When JavaScript on d2qzo95316tvzl.cloudfront.net tries to fetch() something from s3.amazonaws.com, the browser refuses to hand the response back to the script unless the server explicitly opts in with CORS headers. Crucially, this restriction applies to scripted reads, not to navigation — which turns out to matter enormously below.

API Gateway fronts the Lambdas and enforces a hard 29-second integration timeout. A résumé run takes about three minutes. That mismatch is why slice 6a ended with ADR-037: generation is an asynchronous job. POST /resumes/generate writes a pending row, kicks off a background worker, and immediately returns 202 {run_id}. GET /resumes/{run_id} is polled until the row says completed or failed.

The narrow background: what 6a left on the table

So 6b inherits a working contract and needs to build a UI around it. The plan doc, written months earlier, scoped it as "JD input, poll, preview, download, regenerate." Four decisions surfaced in the first hour of reading the deployed 6a code — and two of them turned out to live in the backend, not the frontend.

The pattern worth internalizing: a UI slice that sits on top of a real cloud backend is rarely pure frontend. The browser has rules (CORS, cross-origin download semantics) that the backend must accommodate, and those rules only reveal themselves when you try to render something real.

Wrinkle 1: the preview that CORS would have blocked

The obvious way to show the HTML is to fetch it and inject it:

const html = await fetch(run.html_url).then(r => r.text());  // ✗
<iframe srcdoc={html} />

This fails. The data bucket's CORS configuration allows exactly one method — PUT — because slice 5 only ever needed the browser to upload a résumé. A scripted GET from a different origin gets blocked by the browser before the script sees a single byte.

You could add a GET rule to the bucket. Or you could notice that an iframe's src is a navigation, not a fetch — and navigations were never subject to CORS:

<iframe src={run.html_url} sandbox="" />   {/* ✓ zero infra change */}
This is also the safer option, which is a pleasant coincidence rather than a lucky one. srcdoc content inherits the embedding page's origin, so agent-written HTML would run inside the app's security context. An src to S3 is a genuinely foreign origin, and sandbox="" (which withholds allow-scripts) means no script in that document runs at all. Combined with Jinja2's autoescape=True on the server, agent-generated markup is defended three independent ways.

Wrinkle 2: the download button that didn't download

HTML has an attribute that seems purpose-built for this:

<a href={run.pdf_url} download>Download PDF</a>

The download attribute is silently ignored when the href points at a different origin. It's a deliberate anti-abuse rule: otherwise any page could quietly stamp arbitrary filenames onto files pulled from sites it doesn't control. The result is that the button looks right and behaves wrong — the PDF opens in a browser tab instead of landing in the Downloads folder.

Since the browser won't decide, the server has to. S3 lets a presigned URL carry response-header overrides, and the signature covers them, so they can't be tampered with:

Wrinkle 3: a run costs money and doesn't care if you're watching

Here is the mental model that makes the third decision obvious. The run lives on the server. The browser is a spectator. So consider a user who hits Generate, waits 40 seconds, and reloads the page:

run_id in component staterun_id in sessionStorage
After reloadGone. UI back to an empty form.Restored. Polling resumes.
The run itselfStill running. Still costing $0.31. Completes into a row nobody will ever read.Collected normally.
User's likely next actClick Generate again → $0.62 spent, one résumé receivedWaits ~2 more minutes

Against a $5/month ceiling, orphaning paid runs is a real defect, not a polish item. Three lines of sessionStorage fix it.

The same reasoning caught a second bug. If a double-click fires two POSTs before the first response lands, you get two independent runs — and the second run_id overwrites the first in storage, orphaning a paid run and charging twice. Both buttons now guard on a starting flag.

Code walkthrough

Roughly 400 lines, in four groups. The story runs backend → frontend, because the backend changes are what make the frontend possible.

1. The presign learns about attachments

backend/functions/resume_agent/handler.py:277

def _presign_get(key: str, *, download_as: str | None = None) -> str:
    params = {"Bucket": os.environ["DATA_BUCKET_NAME"], "Key": key}
    if download_as:
        params["ResponseContentDisposition"] = f'attachment; filename="{download_as}"'
    return _s3().generate_presigned_url("get_object", Params=params,
                                        ExpiresIn=_PRESIGN_EXPIRY_SECONDS)

And at the one call site that wants it (handler.py:308):

"html_url": _presign_get(item["html_key"]),                                  # inline → iframe
"pdf_url":  _presign_get(item["pdf_key"], download_as=f"resume-{run_id}.pdf"),  # attachment

Note that the HTML deliberately does not get a disposition — it must stay inline so the iframe can render it. The two artifacts want opposite behaviours from the same bucket, and the presign is where that divergence lives.

A security note worth understanding rather than memorizing: run_id arrives from the URL path, so a user controls what lands inside that filename="…" string. It isn't exploitable, because the code only reaches the presign after get_resume_run(user_id, run_id) returns a stored row, and rows only exist under server-minted ULIDs. But the guardrail is existence-checking, not format-validation — worth remembering if a future change ever lets a client name its own run.

2. A lifecycle rule, and an ADR that couldn't be implemented

infrastructure/template.yaml:549

- Id: ExpireGeneratedResumes
  Status: Enabled
  Prefix: resumes/
  ExpirationInDays: 30

Four lines, but they required amending ADR-015, which had said: keep the most recent generation indefinitely; older generations expire after 7 days. Writing the rule revealed that sentence is not expressible. S3 lifecycle rules filter on prefix, tag, size, and age — there is no "except the newest object" predicate. Honouring it literally would mean re-tagging the previous run's objects on every generation, with a silent failure mode (a missed re-tag keeps objects forever).

Worse, 7 days would have contradicted ADR-037, which gave each run a RESUMERUN row with a 30-day DynamoDB TTL. The row would have outlived its own artifacts by three weeks, and GET /resumes/{run_id} would cheerfully return 200 with presigned URLs pointing at deleted objects. A flat 30 days makes the record and its bytes expire together.

This is the recurring lesson of the whole project: a decision written at design time can be internally reasonable and still be unimplementable on the actual platform. The fix isn't to quietly code something different — it's to amend the ADR with the reasoning, so the next reader learns why.

3. The typed async client

frontend/src/lib/api.ts:211 adds startResumeRun and getResumeRun. The interesting design choice is in the failure branch:

if (b.status === "failed") {
  return { status: "failed", runId, message: b.message as string };
}

The backend already maps seven internal detail codes (budget_exceeded, timeout, render_failed, …) to user-facing sentences. The client passes the sentence straight through rather than keeping a second copy of that vocabulary — so adding a failure mode server-side never requires a matching frontend change.

4. The view: a state machine with a cancellable poll

frontend/src/resume/Resume.tsx:57 models five phases explicitly:

type Stage =
  | { phase: "idle" }
  | { phase: "generating"; runId: string; startedAt: number }
  | { phase: "done"; run: … }
  | { phase: "failed"; message: string }
  | { phase: "abandoned"; runId: string };

The polling effect (Resume.tsx:78) is a setTimeout chain rather than a setInterval — so a slow response can never cause two in-flight polls to overlap — with a cancelled flag closed over by the cleanup function, so unmounting mid-run stops the chain rather than calling setState on a dead component.

Two constants encode real infrastructure limits:

ConstantValueWhy that number
POLL_INTERVAL_MS3,000Keeps the elapsed counter honest across a ~176s wait; ~59 polls per run, each a cheap GetItem (the pending branch doesn't presign).
POLL_CEILING_MS330,000Sits just past the Lambda's 300s timeout. If the worker is killed mid-run it never writes a terminal status, so the row stays pending forever — and a poll with no ceiling would spin forever with it.

That second one is the subtle piece. The agent self-terminates at a 240s wall-clock budget, well inside the Lambda's 300s. The ceiling exists for the case where that budget doesn't save you — a native hang in WeasyPrint, say — and the runtime kills the process with no chance to write failed. The abandoned phase is the honest UI for "we stopped watching; it may still finish."

What the docs had to admit

Architecture §3.2.2 claimed a résumé run targets under 90 seconds. Measured reality is ~176s (82,867 tokens, $0.35 for a run that used its revision). The 90-second figure was written before six sequential Bedrock round-trips existed to measure — and it is load-bearing, not cosmetic: 176s is roughly 6× API Gateway's 29s ceiling, which is why generation is async at all, and it's what every constant in this slice's UI is dimensioned around. Corrected in arch v1.9.
