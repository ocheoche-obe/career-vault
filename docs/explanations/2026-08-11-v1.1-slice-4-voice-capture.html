Background

This slice adds one thing a user can see — a microphone button — and in doing so it disturbs four things nobody could see. That ratio is the reason it is worth explaining rather than merely merging.

The deep background (skip if you already know how browser speech recognition works)

Speech recognition in a browser is exposed through the Web Speech API. You construct a recognizer, set a couple of flags, attach event handlers, and call start(). Audio from the microphone is then turned into text, and the text arrives as a stream of events rather than a single answer at the end.

Those events carry two kinds of result. An interim result is the recognizer's current best guess, and it is allowed to change — you say "I led the" and it might show "I lead the" until more context arrives. A final result is one the recognizer has committed to and will not revise. A single utterance typically produces a run of interims followed by one final.

The crucial thing the name hides: "browser API" describes where the interface lives, not where the work happens. In Chrome and Safari the captured audio is streamed to the browser vendor's speech service and transcribed on their servers. The API even tells on itself — it defines a "network" error code, which would make no sense for on-device processing. Hold on to this; it becomes the most consequential paragraph in the slice.

The API's ergonomics are, to put it gently, of their era. Three behaviours matter here:

  • Continuous mode stops on its own. Even with continuous = true, recognition ends after a silence the page cannot configure. "Keep listening until I say stop" is not something you request; it is something you reconstruct by restarting a session that ended without being asked to.
  • Finals can arrive more than once. The same settled utterance may be reported repeatedly, so anything that naively appends will duplicate text.
  • Chrome and Safari disagree on the details — event timing, and notably whether fragments carry a leading space. "Works in Chrome" is not evidence it works.

The narrow background: where this lands in CareerVault

CareerVault already had a complete text ingestion path, and the whole design goal of this slice was to add nothing to it. A message travels:

Haiku either proposes a structured entry, or — when your message is too vague to parse — routes to ask_clarification and asks a follow-up (FR-2.4). That fallback turns out to matter a great deal for speech, which is messier than typing: filler words, absent punctuation, mangled proper nouns.

There were two composers, and they were not the same shape. Log had a real conversation input: a <textarea> inside a bordered pill, next to a send button. Home had a single-line <input> whose submit navigates to Log carrying the text, which Log then sends immediately. That asymmetry — one box, one line — is where a surprising amount of this slice's work ended up.

What ADR-014 had already decided, in 2026-05-31

Voice was not a new idea; it was a parked one. ADR-014 deferred it to v1.1 and chose the approach in advance: the browser's free Web Speech API, explicitly not Amazon Transcribe, on cost grounds. Against a $5/month ceiling (NFR-1.1) where Bedrock is ~87% of the bill, an API that adds $0 is a strong default.

Slice 3 added amendment 1: a DictationProvider interface with an optional onInterim callback, so that a hypothetical cloud provider — which buffers audio and returns one final transcript — could satisfy the same contract without faking partial results. A required streaming callback would have quietly excluded every non-streaming provider, which is how a seam stops being a seam.

Cross-cloud parallel. The Transcribe-vs-Web-Speech choice has direct analogues: Azure AI Speech and Google Cloud Speech-to-Text are the managed, paid, server-side options. All three would keep audio inside your cloud account and bill per minute. The browser API is the only one that costs nothing — and, as this slice discovered, the only one where you cannot say where the audio went.

Intuition

Voice is an input method, not a pipeline

The single most important design decision is a negative one: dictation adds no backend surface at all. No route, no Lambda, no schema change. The transcript is simply text that arrives in the composer by a different route, and from there it is indistinguishable from typing.

🎙️ Speech
→
DictationProvider
browser
→
Composer text
you review here
→
POST /chat
unchanged

Everything left of the third box is new. Everything right of it already existed.

That framing is what makes the cost claim true, and it is also why the slice could be shipped without a Lambda redeploy.

The review gate, and why it is load-bearing

Dictation fills the field and never sends. You speak, you read what appeared, you edit it, and only then do you submit. This is not politeness — it is the mitigation for speech being messy. An unreviewed send costs a real Bedrock call and deposits a garbled entry in a corpus whose entire value is being trustworthy later.

Once you take that gate seriously, a chain of consequences follows that has nothing to do with speech recognition:

Review before sending
⇒
You must see the text
⇒
A paragraph must fit
⇒
Home needs a textarea

Home's single-line <input> had never been a problem, because nothing on Home had ever produced multi-sentence text. Dictation does. A spoken paragraph in a one-line box scrolls horizontally out of view, and you cannot review what you cannot see. So Home's input became an auto-growing textarea — the same override Log had already made for the same reason.

Whole transcripts, not deltas

Here is the neatest idea in the implementation. The provider's callback does not hand you "the new words since last time". It hands you the complete transcript so far, every time.

Why? Because finals can re-fire. Watch what happens to a naive delta-based consumer when the recognizer reports the same settled utterance twice:

EventDelta-based consumerWhole-transcript consumer
final: "promoted to senior""promoted to senior""promoted to senior"
final: "promoted to senior" (again)"promoted to senior promoted to senior" ❌"promoted to senior" ✓

The delta consumer appends and doubles. The whole-transcript consumer replaces, so a duplicate produces an identical string — the bug becomes a no-op. The contract is idempotent by construction, and no consumer has to know the quirk exists.

Base + transcript, and the trap inside it

The composer may already contain typed text when you press the mic, so the component records a base at start() and composes base + transcript on every update.

base = "I shipped" (captured when you press 🎙️)

transcript: "the"
→ "I shipped the"
→
transcript: "the parser"
→ "I shipped the parser"
→
transcript: "the parser rewrite"
→ "I shipped the parser rewrite"

Elegant — and it contains a trap that a code review caught and the tests did not. What if the field changes while the session is running? Pressing Enter on Log calls setDraft("") and leaves dictation live. The next result recomposes base + transcript and cheerfully puts the message you just sent back into the box. Press Enter again and you have sent it twice, paid twice, and stored a duplicate entry.

The fix is to notice that the premise expired. If the field's text is no longer what this component last wrote, the text the session was appending to is gone — so the session ends. Say-then-send-then-keep-talking now starts a fresh dictation onto whatever is there, which is also what a user would expect.

Pauses, and a bound that only looked like one

Because continuous mode stops on its own, the implementation restarts it — otherwise thinking mid-sentence would end your dictation. But an unconditional restart is a hot loop when the microphone is dead in a way that fires end without ever firing error. So restarts are bounded: three consecutive restarts that capture nothing, and the session gives up.

The counter resets when you speak. Or rather — it was supposed to. The original check was if (settled) silentRestarts = 0, which reads as "reset when there is speech" and means "reset whenever a transcript exists":

You say one word
transcript is now non-empty
→
…for the rest of the session
settled is truthy on every event
→
Any stray result resets the bound
mic stays live indefinitely

Background noise producing an interim that never settles is enough. You walk away, the room is not silent, and the microphone stays open. Keying the reset on the transcript having actually grown makes the bound mean what it always claimed to.

Code walkthrough

1. The contract, and the quirks it refuses to leak

frontend/src/lib/dictation.ts is deliberately two things in one file: a small interface, and a messy implementation of it.

export interface DictationCallbacks {
  /** The complete final transcript since start() — not a delta. */
  onTranscript(transcript: string): void;
  /** Optional. Providers that cannot stream never call it. */
  onInterim?(preview: string): void;
  onError(code: DictationErrorCode): void;
  onEnd(): void;
}

export interface DictationProvider {
  readonly isSupported: boolean;
  start(callbacks: DictationCallbacks): DictationSession;
}

Note what is absent: no mention of restarts, vendor prefixes, interim revision, or silence timeouts. All of that lives below, in webSpeechProvider. That split is the entire point — ADR-014 amendment 3 records that the browser API is inconsistent where it is supported, not merely missing in Firefox, so this file is the one most likely to be replaced.

A small typing detail worth noticing: TypeScript 6's lib.dom types SpeechRecognitionEvent, SpeechRecognitionErrorEvent and the SpeechRecognitionErrorCode union — but not the recognizer itself, presumably because it is still vendor-prefixed in shipping browsers. So the file declares only the missing piece and reuses the built-in event types rather than hand-rolling shapes that could drift.

The result handler writes each final into its own slot rather than appending:

for (let i = 0; i < event.results.length; i += 1) {
  const result = event.results[i];
  const text = result[0]?.transcript ?? "";
  if (result.isFinal) {
    sessionFinals[i] = text;   // re-fired final overwrites, never doubles
  } else {
    interimTail = ...;
  }
}

Restarting after a silence timeout is where the two-level accumulation earns its keep. A restarted recognizer starts with an empty results list, so anything already said must be banked first:

// A silence timeout, not a request to stop.
committed = joinTranscript([committed, ...sessionFinals]);
sessionFinals = [];

joinTranscript exists purely to absorb the Chrome/Safari spacing disagreement — trim each fragment, drop empties, join with a single space — so no consumer has to tidy text it did not produce.

Two error codes are deliberately not errors. no-speech is the silence timeout and aborted is what your own stop button produces; surfacing either would show "something went wrong" to a user who merely paused.

2. The button, and the guarantee it makes structurally

frontend/src/components/MicButton.tsx is shared by both composers. Its most interesting property is something it lacks: it has no access to a submit handler. "Dictation never sends" is therefore not a promise the code keeps by being careful — it is a thing the component cannot do.

Feature detection is a plain early return, and it renders nothing — not a disabled button, not a tooltip:

if (!provider.isSupported) return null;

Typing already works and is the default path, so an absent control leaves no broken affordance and nothing to explain to a Firefox user.

The expired-premise fix from the Intuition section:

useEffect(() => {
  if (!recording || lastEmittedRef.current === null) return;
  if (value === lastEmittedRef.current) return;
  abandonedRef.current = true;   // guard the not-yet-stopped window
  stop();
}, [value, recording, stop]);

The second flag is subtler than it looks. stop() deliberately calls the API's stop() rather than abort(), so a half-spoken word still settles into a final — which means one more result can legitimately arrive after the field was cleared. Without abandonedRef that straggler would repopulate the box, and the fix would have looked correct while remaining broken in exactly the original way.

3. Two composers, one shape

Home's <input> became an auto-growing <textarea> inside a new .composer-field box that also holds the mic — so the mic reads as an affordance of the input rather than a peer of the submit button. Enter sends and Shift+Enter breaks a line, matching Log instead of inventing a second convention for the same keystroke.

That restructure produced two layout bugs, and the pair is instructive because neither was visible to 253 passing tests.

The first was a CSS specificity collision. .input-pill button has specificity (0,1,1); .mic-button has (0,1,0). The descendant selector wins, so the mic silently rendered as a second gradient send button beside the real one:

/* `> button`, not `button`: the mic also lives inside the pill, and a
   descendant selector here outranks its own class rule. */
.input-pill > button { ... }

The second was subtler and got past a mobile check. .composer-row moved from align-items: stretch to flex-end — correct in a row, because buttons should track the last line of a growing field. But the @media (max-width: 768px) block flips to flex-direction: column, and in a column align-items governs the horizontal axis. The full-width "Start logging" CTA collapsed to its content width and hugged the right edge.

Why the mobile pass missed it. The check asserted zero horizontal overflow at 375px, and that assertion was true — a button that has shrunk overflows nothing. The invariant held and the layout was still wrong. The lesson recorded for the next UI slice: compare geometry against the pre-change layout, not only against invariants.

4. The entry card: an error that named a field nobody had

Dictating a real entry surfaced a bug that predates this slice entirely. Typing August 3, 2026 into a date field produced a rejection saying "fix the highlighted fields" — with nothing highlighted.

The cause is a lovely little impedance mismatch. career_crud/handler.py:74 builds each error's field name by joining Pydantic's whole loc tuple:

{"field": ".".join(str(part) for part in err["loc"]), "error": err["msg"]}

The entry schema is a discriminated union over entry_type, so loc for a bad project date is ("PROJECT", "start_date") → "PROJECT.start_date". The client's field key is plain start_date. The comparison was e.field === key, which never matched — so every field-level 422 fell through to the "unknown field" catch-all, for as long as both have existed.

export function fieldMatches(errorField: string, key: string): boolean {
  return errorField === key || errorField.split(".").at(-1) === key;
}

Fixed on the client rather than the server, deliberately: matching the last segment leaves the API contract untouched, keeps the genuinely-unknown-field path working, and kept the slice frontend-only with no Lambda redeploy. The card's catch-all uses the same predicate, so an error is reported inline or in the fallback — never both.

The date fields also now state YYYY-MM-DD up front, because Pydantic's rejection ("invalid character in year") says what is wrong and never what would be right.

5. The correction that mattered most

The security review returned one finding, and it was a documentation defect rather than a code one. ADR-014 had described Web Speech as "browser-side" since the day it was written, and repeated it in both amendments.

That phrasing is true of the API and false of the processing. Chrome and Safari stream audio to the vendor's speech service. Before this slice, no audio left the device; after it, speech containing employers, dates, project detail and colleague names is transmitted to a third party — outside the SSE-S3/DynamoDB boundary every other part of the system is designed around.

The decision survived; the reasoning did not. The "$0" claim was always about AWS spend, and it is still exactly right — nothing bills to the account. What was wrong was an implied containment guarantee the ADR never had grounds to make. Rejecting Amazon Transcribe on cost reads, in hindsight, as though the browser option were also the more contained one. It is the opposite: Transcribe would have kept the audio inside the AWS account.

Two mitigations shipped. The recording status line now says where the audio goes, while it is going there — an undisclosed data flow was the actual defect, since the flow itself is inherent to the chosen API. And the capture window got the bound described earlier, so a live microphone cannot outlive the user's attention indefinitely.

The general habit worth taking from this: a cost argument is not a privacy argument, and an ADR that settles one should not be read as having settled the other.
