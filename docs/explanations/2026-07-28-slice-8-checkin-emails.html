Background

Every slice of CareerVault so far has had a person on the other end. You type into the chat box and wait for a reply. You click Generate and watch a progress counter. You press Save and see the row appear. When something breaks, you notice, because you were standing there.

Slice 8 builds the first feature where nobody is standing there. Once a day, a timer fires, a function wakes up, decides whether you're due for a nudge, composes an email, and sends it. If it silently stops working, the only symptom is an email that doesn't arrive — and an email that doesn't arrive looks exactly like an email that wasn't supposed to arrive. That single fact drives most of the design decisions below, so it's worth holding onto.

Skippable: the AWS pieces, if you haven't met them

If you already know EventBridge Scheduler and SES, jump to the next heading.

EventBridge Scheduler is AWS's cron service. It is not the same thing as EventBridge Rules, which are the older cron-ish triggers built into the EventBridge event bus. Rules cap at 300 per account and have thin retry configuration; Scheduler was purpose-built in late 2022 for invoking things on a schedule, supports millions of schedules, and — the part that matters here — has native per-schedule retry policies and dead-letter queues. The cross-cloud equivalents are Azure Functions' Timer trigger and GCP's Cloud Scheduler.

One quirk worth internalising: Scheduler invokes your Lambda by assuming an IAM role you give it, not through a resource-based policy on the function. If you've wired up an S3 or SNS trigger before, you'll have written an AWS::Lambda::Permission saying "this service may invoke me". Scheduler doesn't work that way — you hand it a role that has lambda:InvokeFunction, and it calls as that role. That's why there's an AWS::IAM::Role in this diff and no Permission resource.

SES (Simple Email Service) sends email. Two operational facts shape this slice. First, new SES accounts start in sandbox mode, where you may only send to addresses you have verified — which is normally a nuisance, but for a single-user app it's simply free correctness. We checked the live account at slice start: ProductionAccessEnabled: false, 200 sends/day, zero verified identities. Sandbox is genuinely sufficient here, so it's documented rather than escalated.

Second, verifying an email identity means clicking a link in an inbox. CloudFormation can create the identity and cause the verification mail to be sent, but it cannot click the link. So the stack reaches CREATE_COMPLETE with the identity still PENDING, and every send fails with MessageRejected until a human intervenes. This is a genuinely useful thing to know about infrastructure-as-code: a resource being "created" is not the same as it being usable.

Where this lands in CareerVault

The pieces that already existed and that slice 8 builds on:

  • A single DynamoDB table, CareerVaultTable-dev, holding everything (ADR-005). Each user's items share one partition key, USER#<sub>, and are distinguished by sort-key prefix: PROFILE, ENTRY#<ulid>, CONVO#…, and now CHECKINLOG#<ulid>.
  • No global secondary indexes at all (ADR-028). This turns out to matter enormously, as we'll see.
  • PUT /settings, which shipped early with backlog item B-008 so that generated résumés could have a name on them. It writes name, location, phone — and deliberately refused to write anything else.
  • A shared Lambda layer, careervault-shared, carrying the Pydantic models, the Bedrock wrapper, and the DynamoDB helpers.

Intuition

Strip away the AWS vocabulary and the feature is four sentences: once a day, look at everyone; work out who's due; write them something; remember that you did. Each of those four sentences turned out to contain a decision worth arguing about.

1. One daily alarm, not one alarm per cadence

FR-4.1 wants four cadences — weekly, biweekly, monthly, quarterly — and FR-4.6 wants the user to change theirs whenever they like. The obvious implementation is a schedule that matches the cadence: cron(0 23 ? * FRI *) for weekly.

The obvious implementation is wrong, and the reason generalises well beyond this project. If the schedule encodes the cadence, then changing your cadence means mutating infrastructure — an API call to EventBridge Scheduler that can fail independently of the database write that recorded your preference. Now you have two systems that can disagree about how often you want email, and no transaction spanning both.

So instead: the schedule fires daily and knows nothing about cadence. Each user's PROFILE carries a next_checkin_at timestamp, and the daily run simply asks "is it past that yet?". Cadence becomes a data question.

Daily fire
23:00 UTC
→

next_checkin_at?
→
send, then
next += cadence

Weekly user: fires 7 times, sends once. Quarterly user: fires 91 times, sends once. Same schedule.

The transferable idea. A frequent fixed trigger plus a due-timestamp in your datastore beats one trigger per entity, as soon as the schedule becomes user-configurable. You trade precise per-entity timing for a system where changing a schedule is a database write instead of a control-plane operation — and control-plane operations are the ones that fail in ways your transaction can't roll back. Azure Functions Timer + a due column, or Cloud Scheduler + a Firestore nextRunAt, are the same design. This is ADR-039.

2. "Query the profiles that are due" is not a thing you can do

The architecture document, written months earlier, said the Lambda "queries PROFILE items where next_checkin_at <= now". That sentence reads perfectly and cannot be implemented.

In DynamoDB, a Query must begin by naming a single partition key. But every user's PROFILE lives under a different partition key — that's the whole point of the single-table design. So "all PROFILEs across all users" isn't a query result; it's a property of the whole table. Reaching it requires either a global secondary index (which ADR-028 explicitly declines to ship) or a Scan.

QueryScan
Starts fromOne partition key you nameThe entire table
Can it find "all PROFILEs"?No — they're in different partitionsYes
Cost here—48 items scanned to find 1, ~1 RCU, once a day

The correction matters more than the word choice suggests. Reading the doc, you'd think a GSI was a performance upgrade you could defer. It isn't: a GSI is what would make this a Query at all. The architecture doc is corrected to v2.1 accordingly — and the same wrong word appeared a second time in §4.5.4, describing how the bounce handler finds a user by email address. Same reason, same fix.

3. Three tiers, and only one of them is a real fallback

FR-4.5 says: "If LLM personalization fails or exceeds cost budget, the system shall fall back to a generic reminder." The architecture doc answered this with a mode flag — personalized when you have recent entries, generic when you don't.

But look closely: that's answering a different question. "You had a quiet week" is a content problem. "Bedrock is throwing 500s" is an availability problem — and both of those modes call Bedrock, so neither survives it. The doc's fallback depends on the thing it claims to be a fallback for.

The rule worth stealing: the last tier of a fallback chain must not depend on any service the tiers above it depend on. Otherwise it isn't a fallback — it's a retry. Tier 3 makes no Bedrock call at all, which is why the check-in path has no hard dependency on Bedrock availability. This is ADR-021.

And the "exceeds cost budget" clause? We deliberately do not meter spend at send time. A Cost Explorer read is hours stale, needs its own IAM grant, and the thing it would be guarding costs $0.0026. Instead the prompt is bounded by construction: at most 15 entries, each truncated to 400 characters, with a small output cap. There is no state in which a run could overrun. Cap the input, not the invoice.

4. Sending twice is worse than sending once

EventBridge Scheduler is at-least-once. If your Lambda times out halfway through, Scheduler retries — and if the timeout happened just after SendEmail returned, you've already sent the email. Retry naively and the user gets two.

The fix is to claim the right to send before sending, using a conditional write that only one racer can win:

compose
→
claim slot
conditional UpdateItem
→
SES send
→
CHECKINLOG

Both neighbours of "SES send" are placed deliberately.

Claim before the send, so a retry loses the conditional write rather than the mailbox absorbing a duplicate. Audit after the send, so a CHECKINLOG row means "SES accepted this" rather than "we intended this". Both orderings are asserted in the tests, not merely commented, because both are easy to get backwards and neither failure is visible in normal operation.

The price of this ordering. If SES fails after the claim, you're marked as sent and your next nudge is a full cadence away. That's not a bug you can fix by reordering — claiming afterwards just trades it for duplicates. Idempotency buys "at most once" by giving up "at least once", and no ordering gives you both. For a nudge that's the right trade; for a billing notice it would be the wrong one. Logged as backlog B-016 so the reasoning gets re-derived rather than inherited.

5. Updating one field inside a nested object

Cadence and pause both live inside a nested settings object on the PROFILE item, and FR-4.6 needs them to move independently. The natural-looking write destroys that:

// You send just the pause:
{ "settings": { "checkin_paused": true } }

// A naive UpdateItem compiles it to:
SET settings = { "checkin_paused": true }

// Stored before: { checkin_cadence: "monthly", checkin_paused: false }
// Stored after:  { checkin_paused: true }        ← cadence is gone

DynamoDB's partial-update semantics work per top-level attribute. Assigning to settings replaces the whole object. The write succeeds, returns 200, and the response body looks entirely plausible — you only find out days later when your check-in arrives at the wrong cadence.

This trap was spotted during the B-008 review and the field was withheld rather than shipped broken, logged as B-014 for whoever needed it first. Slice 8 is that consumer. The fix is document paths: name the sub-field, not the object.

SET settings.checkin_paused = :v     ← surgical; siblings untouched

Two things make that actually work, and both were probed against the live table before the ADR was finalised rather than assumed:

PremiseReality
Can you write settings.x when settings doesn't exist?No. ValidationException: The document path provided in the update expression is invalid — and no PROFILE in the live table had a settings attribute, so every write would have failed.
Can the seed ride along in the same expression?No. Two document paths overlap with each other — you may not name both settings and settings.x in one expression.
Does writing one sub-field preserve its siblings?Yes — the property FR-4.6 actually needs.

The second row is the interesting one, because the first draft of ADR-040 asserted the opposite as fact. It said the seed and the sub-paths would share one expression. Running it took thirty seconds and disproved it. The final design issues a separate, idempotent seeding UpdateItem first — and the ADR now records the correction alongside the decision, because a reader deserves to know which parts were verified.

Code walkthrough

Roughly 1,400 lines of implementation and 950 of tests, across two new Lambdas, one shared module, and a sizeable chunk of SAM template. Here's the story rather than the file list.

The arithmetic, extracted first

backend/shared/python/careervault/checkin_schedule.py holds every rule about when — and nothing about AWS. Pure functions, no clients, no mocks needed. That extraction is deliberate: this is the logic whose bugs are invisible, so it's the logic most worth testing exhaustively.

Three decisions in there are worth reading closely, because each picks a direction to fail in:

def is_due(profile, now):
    if is_paused(profile):        return False
    if not profile.get("email"):  return False
    due_at = parse_iso(profile.get("next_checkin_at"))
    return due_at is None or due_at <= now   # absent → due now

Absent means due. That's how every PROFILE written before this slice seeds its own cycle on the first run, with no backfill migration. An unparseable timestamp also means due — failing toward sending, because a garbled value that silently suppressed email forever would be undetectable. And is_paused compares against True explicitly rather than truthily, so a stray string "true" does not pause you: the failure direction is "we sent mail you didn't want" (visible, fixable) rather than "we stopped forever" (invisible).

utcnow_iso looks cosmetic and isn't:

"2026-07-31T23:00:00Z"      ← what we store
"2026-07-31T23:00:00+00:00" ← the same instant, different bytes

The idempotency condition compares these with DynamoDB's <, which is lexicographic. '+' is 0x2B and 'Z' is 0x5A, so the two formats sort differently for the same moment. Mixing them would break the duplicate guard silently. There's a test asserting the exact format.

The nested merge

ddb_helpers.py's update_profile now pulls settings out before the main loop — so it can never reach the top-level compiler that would replace it — issues the idempotent seed if there's anything to write, then compiles one document path per sub-field.

The matching guard on the way in is in profile.py. SettingsUpdate is a separate model from Settings for one reason: every field must be optional with no materialisable default. If checkin_cadence had its usual "weekly" default here, a request touching only checkin_paused would emit checkin_cadence: "weekly" on its way past and reset a monthly user — the original bug, reintroduced one level down and much harder to see, because the offending value is a default rather than something anyone sent.

The handler relies on Pydantic's exclude_unset reaching into the nested model. That's load-bearing enough that it was verified before being depended on, and there's a test at the handler boundary pinning it.

Composition and its three tiers

composer.py builds the prompt, calls Haiku through the shared client with a single forced tool (compose_checkin), and validates the result. Its except is deliberately a bare Exception:

except Exception as exc:
    logger.warning("Check-in personalization failed; falling back to static tier", ...)
    return _static_email(profile), "static"

Narrowing that would mean a new Bedrock failure mode escapes to the caller and turns a degraded send into no send. The set of things Bedrock can raise is open-ended and every one of them has the same correct answer.

There's also a guard the prompt alone can't provide: in the generic tier, any recent_activity_summary the model produced is stripped in code. The system prompt tells it not to invent activity; the code doesn't rely on that. It's the one field where a hallucination is actively misleading — an email describing work you never did — rather than merely bland.

The scheduled loop

handler.py is the shape a batch job wants. Every per-user iteration is wrapped:

for profile in due:
    try:
        outcome = _process_user(profile, now, run_id)
    except Exception:
        logger.exception("Check-in failed for user", extra={"user_id": user_id})
        metrics.add_metric(name="CheckinsFailedUser", ...)
        outcome = "failed"

One unverified recipient must not cost every other user their check-in. And when nothing is due — which is most days at a weekly cadence — the run emits CheckinsNoDueUsers rather than returning quietly. That metric is what distinguishes "nothing to do" from "the job never ran", and those look identical from the outside. This is the whole discipline of §3.3.5: a user-facing flow fails loudly to someone who can react; a scheduled flow fails silently to nobody, so you have to manufacture the loudness yourself.

The same instinct shows up in the alarms in template.yaml. Every other function in this stack alarms at "more than 5 errors in 5 minutes" — sensible for something a human retries. This one alarms at zero: it runs once a day, so five errors would take five days to accumulate, by which point five check-ins never went out.

Bounce handling

ses_event_handler/handler.py is the smallest function in the system. SES publishes Bounce and Complaint events to a Configuration Set, which forwards them to an SNS topic, which invokes this. It resolves the recipient to a user and stamps the PROFILE.

Note the topic is deliberately not the alarm topic (§4.5.5). Alarms are rare and must be noticed; SES events are routine. Sharing one topic trains you to ignore the page. Similarly there are two DLQs for two different invokers — Scheduler→Lambda failures and SNS→Lambda failures are separate mechanisms configured at different layers, and either can fire without the other.

At MVP this handler records and alarms but takes no automated action. Auto-pausing after repeated bounces is the tempting feature and the risky one: the first thing it does when it misfires is silently stop something that works.

Two fields the docs described that never existed

The generic fallback was documented as referencing profile.aspirational_goal. That field did not exist on the model. Without it, tier 2 has nothing to say and quietly degrades to tier 3 for every user, forever. It was added.

The multi-tenant note claimed PROFILE already had checkin_time_local. It never did — and it was deliberately not added, because MVP ships one fixed UTC fire time and a field nothing reads is worse than an absent one: it implies a capability that doesn't exist.

This is exactly the B-008 failure mode, twice, in one feature: _contact_from_profile read name and location from a model that had never had them. The pattern is worth naming — prose describing a data model drifts silently, because nothing fails when a field in a sentence never becomes a field in a schema. Code that references a missing field crashes; a document that references one just sits there being wrong.

What the live run taught us

The first personalized send came back as tier 3. Haiku had returned a complete, well-written email that omitted sign_off — a field the tool schema lists as required. Pydantic rejected it, and a good email was discarded in favour of the static template.

The lesson is that required in a Converse tool schema is a strong hint, not a constraint. The generic send a minute earlier had included the field; same prompt, same temperature 0. (This project has hit model non-determinism at temperature 0 before.) The fix isn't a looser schema — it's noticing that not all fields carry the same weight:

FieldTreatmentWhy
subjectstrictNo subject, no email
promptsstrict, min 1No prompts and it isn't a check-in, just a greeting
greetingdefaultsFraming, not content
sign_offdefaultsFraming, not content

Validate what makes the output useful; default what merely makes it polished. A schema that's strict about cosmetics converts recoverable model variance into a visible downgrade — and because the email still arrives, that downgrade is invisible without the CheckinsStaticFallback metric.

A test-harness bug this slice flushed out

Adding checkin/rendering.py broke the résumé agent's tests. In Lambda each function is its own deployment package, so from rendering import ... unambiguously means "the file next to me". Under pytest every function directory is visible at once, and the import resolved to whichever landed on sys.path first. helpers.py's load_handler now isolates each load and evicts the siblings afterwards, so filename collisions between functions stop being a latent trap.

Verified live

All three tiers produced real emails and audit rows; both idempotency layers were exercised separately (the due-ness gate, and the conditional claim under the actual Scheduler-retry shape); pause suppressed a send without disturbing the schedule; a weekly→monthly switch paced the next cycle at 30 days rather than 7; and a bounce driven through the SES mailbox simulator travelled SES → Configuration Set → SNS → handler → bounce_count: 1 on the PROFILE. Cost: ~$0.0026 per check-in, about a penny a month.

Quiz

Why does the daily EventBridge schedule fire every day rather than matching each user's cadence, given that a weekly user only needs an email once a week?

The architecture doc said the Lambda "queries PROFILE items where next_checkin_at <= now". Why was this corrected to a Scan rather than kept as a Query with a GSI noted as a future optimisation?

The check-in claims its send slot with a conditional write BEFORE calling SES, and writes the CHECKINLOG audit row AFTER. What would go wrong if both were moved to after the SES call?

SettingsUpdate is a separate Pydantic model from Settings, with every sub-field optional and no defaults. What specifically breaks if checkin_cadence carried its usual "weekly" default on the update model?

Haiku returned a complete check-in email but omitted sign_off, a field the tool schema marks as required — and the run fell back to the static tier. What does this reveal about tool-use schemas, and what was the fix?
