Two items, two lifetimes: how a résumé stopped expiring

Background

This slice is about a single, deceptively small question: how long does a résumé live? Answering it properly required a new DynamoDB entity, a new API route, deleting an S3 lifecycle rule, and — a day later — adding a delete button that the answer itself made necessary. It is a good example of how one retention decision ripples outward through a system.

Skippable background: the three AWS pieces in play

If you already know DynamoDB TTL, S3 lifecycle rules, and why a long job can't be a normal HTTP request, skip to the next heading.

DynamoDB TTL is a per-table setting that names one attribute — here expires_at — holding a Unix timestamp. A background process sweeps the table and deletes items whose timestamp has passed. The crucial detail, and the hinge of this entire slice: TTL only ever deletes items that actually carry the attribute. An item without expires_at is not "an item with an infinite expiry" — it is invisible to the sweeper. So "make this durable" is not a configuration change. It is an omitted field.

Cross-cloud parallel. Azure Cosmos DB has the same mechanism with the opposite default: a container-level DefaultTimeToLive plus a per-item ttl override, where -1 means "never expire". Google Firestore uses a TTL policy on a timestamp field, much like DynamoDB. In all three the pattern is identical — expiry is data, not schema.

S3 lifecycle rules are the object-storage equivalent, but they are coarser. A rule matches on prefix, tag, size, or age — and that is the whole vocabulary. It cannot express "keep the newest one, expire the rest", which is exactly the rule this project originally wrote down and later discovered was unimplementable (that correction is the first ADR-015 amendment, from slice 6b).

Asynchronous jobs. API Gateway caps a REST integration at 29 seconds. A résumé run takes about 176 seconds — six sequential Bedrock round-trips through Claude Sonnet. So generation cannot be a request/response call. Instead (ADR-037): POST /resumes/generate writes a pending item, invokes the same Lambda asynchronously, and returns 202 {run_id}. The browser then polls GET /resumes/{run_id} every 3 seconds until the status turns terminal.

The narrow background: what the trace was for

That polling design produced an item called RESUMERUN#<run_id> — the run trace. It holds the job status plus the agent's exhaust: which entries were retrieved, how many retrieval iterations ran, how many revisions the critique forced, token counts, cost, and a phase-by-phase log. It exists so a run can be polled and, afterwards, debugged. It carries a 30-day TTL.

Here is where the trouble started. The generated HTML and PDF live in S3 under resumes/<user_id>/<run_id>/. If the trace vanished at 30 days but the objects lingered, you would have artifacts nothing referenced. So slice 6b added an S3 lifecycle rule expiring resumes/ at 30 days too — not because 30 days was the right lifespan for a résumé, but to stop a pointer outliving the thing it pointed at.

That is a coupling fix masquerading as a retention policy, and it quietly capped the product: the Résumés view could never show you anything you built last quarter. The backlog called this B-028, and it blocked the last un-redesigned view.

Intuition

The insight in ADR-046 is that RESUMERUN# was doing two unrelated jobs at once. It was the job record a client polls, and it was the résumé the user owns. Those two things have genuinely different lifetimes, and the moment you notice that, the 30-day number stops being a policy and starts being an accident.

So the slice splits them. One run now writes two items:

One completed run
run_id = 01JB…
→
RESUMERUN#01JB
agent exhaust: trace,
retrieved_ids, iterations
expires_at set → gone in 30 days
↳
RESUME#01JB
the résumé: target_title,
created_at, document, S3 keys
no expires_at → durable

Same run, seen twice: the résumé you built, and the machinery that built it. The exhaust is allowed to expire on schedule. The résumé is not.

The prefix hazard, and why the # is load-bearing. RESUME# and RESUMERUN# differ at the seventh character. Listing history queries begins_with("RESUME#") — and that correctly excludes traces only because the # is part of the prefix string. Drop it and begins_with("RESUME") silently matches every trace too. One character separates a correct query from one that returns twice the rows it should.

Listing history without a secondary index

The obvious way to fetch "my résumés, newest first" is a GSI sorted by date. This project has no GSIs (ADR-028), and did not need one here. The reason is in the ID format: every ID is a ULID, which begins with a 48-bit timestamp, so ULIDs sort lexicographically in the order they were created. The sort key already is a time index.

SK: RESUME#01JA…
22 Jul
<
SK: RESUME#01JB…
28 Jul
<
SK: RESUME#01JC…
03 Aug
ScanIndexForward=False reads that same range backwards → newest first, one Query, no index

The query is also projected: it asks for five attributes rather than whole items. This is not micro-optimisation. A RESUME# item stores the full pasted job description and the entire structured résumé — potentially tens of kilobytes — and the history grid renders none of it. Fetching it all would bill read capacity and transfer megabytes to draw a list of cards.

The bug the split would have shipped

Making artifacts durable while the trace still expires creates a gap that only appears after 30 days:

Day 29
list shows the row
→
View → GET /resumes/{run_id}
reads the trace → 200 OK
Day 31
list still shows the row
→
View → trace has TTL'd
→ 404, on a résumé that plainly exists

The fix is a fallback: when the trace is gone, the status endpoint reads the durable record instead. A list must never offer a row whose button fails.

The consequence nobody asked for

Removing the lifecycle rule removed the only thing that ever cleaned up a résumé. Under the old regime you never needed a delete button, because everything left on its own. Making résumés permanent quietly created that gap — which is why deletion was added mid-slice, as a second amendment to the same ADR that had just been accepted.

And deletion across two services has no transaction. S3 and DynamoDB cannot be updated atomically, so a crash between them leaves an inconsistency; the only choice is which inconsistency:

OrderIf it crashes halfwayRecoverable?
Record first, then S3Objects nothing references, and nothing will ever expire them. The user cannot even see the résumé to retry.❌ Invisible and permanent
S3 first, then recordA history row whose View fails — annoying, obvious, and deletable again (S3 deletes are idempotent).✅ Visible and retryable

A visible, retryable fault beats an invisible, permanent one. So objects go first — the exact inverse of the write path, and for the exact same reason.

Code walkthrough

1. The durable item is defined by what it omits

backend/functions/resume_agent/handler.py:195 builds the record. The whole of ADR-046 is the absent line:

return {
    "PK": f"USER#{user_id}",
    "SK": f"RESUME#{run_id}",
    "entity_type": "RESUME",
    "target_text": target_text,          # full, not truncated — see below
    "target_title": _target_title(target_text),
    "html_key": keys.get("html_key"),
    "pdf_key": keys.get("pdf_key"),
    "document": …,
    # No `expires_at`. That omission *is* the durability.
}

The title is derived deterministically — the first non-empty line of the pasted target, which is the job title in every realistic paste. No Bedrock call to label a row; against a $5/month ceiling, spending money to generate a card heading would be absurd.

A bug the code review caught here. The record originally stored target_text[:4000], copied from the trace. But 4,000 characters was chosen for an item that expires in 30 days. Applying it to a permanent record silently discards two-thirds of a long job description — irreversibly, and in direct contradiction of ADR-046 §4, which keeps the full text precisely because the planned gap-analysis feature will read it. Truncation on a permanent record is unrecoverable; the trace keeps its bound, the record does not.

2. Write ordering, and why it is not a transaction

DynamoDB offers TransactWriteItems, and this deliberately does not use it. The worker finalizes the trace first, then writes the record inside its own try/except: a failed history write must never turn a completed run into a failed one for the user. The run succeeded; the user has their résumé. The cost of that choice is a possible orphan, logged honestly as B-039.

3. The list query

ddb_helpers.py:409:

response = get_table().query(
    KeyConditionExpression=(
        Key("PK").eq(pk_for_user(user_id)) & Key("SK").begins_with("RESUME#")
    ),
    ScanIndexForward=False,        # newest first — ULIDs make SK order time order
    Limit=limit,
    ProjectionExpression="run_id, created_at, target_title, entry_count, #status",
    ExpressionAttributeNames={"#status": "status"},
)

Note #status. status is a DynamoDB reserved word, so naming it directly in a projection is a syntax error; you alias it. There are several hundred such words, and this is the everyday way you meet them.

Known limit, logged not hidden. This caps at 50 rows and discards LastEvaluatedKey. Past 50 résumés a row becomes not merely unlisted but unreachable — both View and Delete need a run_id the UI can only learn from the list. At roughly one résumé a week that is about a year away, so it ships as B-043 rather than being patched at wrap time.

4. Deletion, and three bugs worth studying

handler.py:446 is the newest code in the slice and produced three of the four serious review findings. All three were fixed by one structural change: read the record before destroying anything.

record = get_resume_record(user_id, run_id)
if record is None:
    return _response(404, {"message": "That résumé no longer exists."})

keys = [k for k in (record.get("html_key"), record.get("pdf_key")) if k]
result = _s3().delete_objects(Bucket=bucket, Delete={"Objects": [{"Key": k} for k in keys]})
errors = result.get("Errors") or []
if errors:
    return _response(500, {"message": "Couldn't delete that résumé — please try again."})

Bug one: a 404 that destroyed things. The original deleted objects and the trace before discovering the record was absent. So DELETE on a run that was still pending destroyed the trace of a live ~$0.31 Sonnet job — the user's poll would then report "expired" while the job merrily continued — and for a failed run it destroyed the only diagnostic record, while replying "no longer exists".

Bug two: delete_objects does not raise. This is the one worth carrying to other projects. The S3 batch-delete API returns HTTP 200 with a per-key Errors list. A failure on one key is not an exception:

{"Deleted": [{"Key": "…/resume.html"}],
 "Errors":  [{"Key": "…/resume.pdf", "Code": "InternalError"}]}

So except ClientError never fired, the record was deleted anyway, and the PDF was stranded forever — precisely the orphaning the S3-first ordering exists to prevent. The careful docstring argued for the right ordering; the code silently opted out of the argument.

Why the test did not catch it. The fake S3 client returned None from delete_objects. The handler's error check therefore had nothing to check and passed vacuously. A test double that is wrong in the same way as the code proves nothing. The double now returns the API's real shape, and reverting the check fails exactly one test.

Bug three: reconstructed keys. The keys were rebuilt as resumes/{user}/{run}/resume.html from today's naming convention, while the record already stored the authoritative ones. Any record written under a different layout — a backfilled one, or anything after a future path change — would have had its row deleted and its real objects left behind. Reading the record supplies them.

5. The frontend, and one honesty rule

Resume.tsx was rebuilt against the design handoff. The handoff specified four status badges — Latest, New, Sent, Draft. There is no send path (ADR-015 is in-app download only) and no draft state, so two of the four describe features that do not exist. Under ADR-045 they are omitted rather than faked.

The same rule caught a subtler violation in review. The generator card read "Pulls the 13 records in your vault…", where 13 came from the newest history row's entry_count — which is how many entries that one run retrieved for that one target, a subset that changes with every unrelated run. A user with 27 entries was told they had 13. The number was real; the sentence it appeared in was false. The true count already existed in the app shell and is now passed down.

A $0.31 button. Regenerate reran whatever sat in the target textarea. Open a three-month-old résumé from history and press it, and you would spend $0.11–$0.35 of Sonnet against an unrelated job description while the screen showed the old résumé. No endpoint returns the original target_text, so there is nothing to regenerate from — the button is simply not offered on a history-opened résumé.

6. Theme selection, and the first-frame problem

Users can now pick Light, Dark, or System. The interesting part is where the code runs. A stored preference read by React arrives after the bundle parses and the first frame paints — so the app would flash the wrong theme on every load. The read therefore happens in a synchronous inline script in index.html, before first paint:

<script>
  try {
    var t = localStorage.getItem("careervault:theme");
    if (t === "light" || t === "dark") document.documentElement.dataset.theme = t;
  } catch (e) { /* storage unavailable — fall through to the system preference */ }
</script>

"System" is represented by the absence of the attribute, letting the existing prefers-color-scheme media query take over — the same omission-as-mechanism idea as the missing expires_at, one layer up the stack. A test asserts this script and the TypeScript module agree on the storage key, because they are two copies of one contract that no compiler checks.

7. Migrating the résumés that already existed

Six real résumés predated ADR-046: they had traces but no records, and their traces were due to expire between 21 and 28 August. After that their S3 objects would have had nothing to list them, nothing to poll, and — since this slice removed the lifecycle rule — nothing to clean them up. scripts/backfill-resume-records.py builds the missing records, dry-run by default and idempotent via attribute_not_exists(SK).

Two failures it hit are worth knowing because only a script that actually reads the table can hit them: the table name is read from the environment by the shared helper (the dry run never reached that code path), and DynamoDB returns numbers as Decimal, which json.dumps cannot serialise — so values must be converted before being written back. The review added a third: the query never followed LastEvaluatedKey, so a migration racing a TTL deadline could have silently skipped everything past the first 1 MB page and still exited 0.
