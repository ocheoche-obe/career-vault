Background

Every slice before this one added a feature. Slice 9 adds none. Its job is to answer a harder question: is the thing we built actually what we said we built? That makes it the most transferable slice in the project, because the techniques here — cost-aware test design, running a real database engine locally, planning an infrastructure deploy without performing it — apply to any system, not just this one.

Skippable primer: what "testing" means for a serverless app

If you already know the test pyramid, skip to the next heading. Otherwise, the thing that makes serverless testing awkward is that most of your application is not your code. A CareerVault request touches CloudFront, Cognito, API Gateway, a Lambda role's IAM policy, a Lambda layer, DynamoDB, and Bedrock. Your Python is a thin filling in a very large sandwich.

So there are three quite different questions you might be asking, and they need three different kinds of test:

QuestionKind of testWhat it fakes
Does my logic branch correctly?UnitEverything external — DynamoDB, Bedrock, S3 are all stand-ins
Does the database behave as I assumed?Local integrationNothing about the database; it runs for real, just on your laptop
Does the deployed thing work?Cloud integrationNothing — real IAM, real table, real Lambda

CareerVault had 370 tests before this slice and all of them were the first kind. That is not a small gap. A unit test that fakes DynamoDB can only check that your code asked for the right thing; it can never tell you whether DynamoDB would have agreed.

The bug that motivated all of this. An earlier slice shipped a bug where a Lambda wrote an item with the wrong sort-key prefix. Every unit test passed, because the tests asserted on the string that was passed to a fake. Nothing checked what a real engine would do with it. Architecture §5.6 has asked for a DynamoDB-Local safety net ever since.

DynamoDB Local

DynamoDB Local is the actual DynamoDB query engine, packaged as a Docker container that listens on localhost:8000. It is not a mock and not a reimplementation — it speaks the real wire protocol and enforces the real rules. If you write a ConditionExpression that DynamoDB would reject, DynamoDB Local rejects it, with the same error code.

CareerVault was already built to accommodate this. get_table() in the shared layer reads an optional DDB_ENDPOINT_URL; set it, and every helper in the codebase transparently talks to your laptop instead of AWS. That one environment variable is the whole seam.

CloudFormation change sets

The second technique worth knowing. sam deploy normally computes what needs to change and then does it. --no-execute-changeset stops after the computing: CloudFormation validates the template, resolves every conditional, works out the exact list of resources it would create — and then hands you that list and waits.

This is the same primitive as terraform plan, Azure's what-if, and gcloud deployment-manager --preview. It costs nothing and creates nothing.

Intuition

Idea 1: sort your tests by what they cost, not by how fast they are

The usual axis for splitting a test suite is speed — "unit" versus "slow". CareerVault has a different constraint. Bedrock charges per token, and one tailored-résumé run costs real money. The project runs under a $5/month ceiling. So the meaningful question about a test here is not "how long does it take?" but "what does it cost to run?"

Work through the arithmetic and the design falls out on its own. Suppose you write one uniform suite that exercises everything, résumé agent included:

One suite
~$0.35/run
→
$5 ceiling
÷ $0.35
→
~14 runs
per month

Fourteen runs is not a test suite. It is a budget you spend nervously.

A suite you can only run fourteen times a month is a suite you don't run. You skip it before a small commit, you skip it when you're in a hurry, and eventually you skip it always. And here is the part that matters:

An avoided test is worse than an absent one — because it still appears in the repo, still gets counted, and still implies coverage that nobody is actually getting.

So the tests are tiered by price, and the default tier is free:

TierRuns againstCostIn the default run?

cloudThe deployed dev stack, no model calls$0✅ yes

56 tests run for nothing, in about 15 seconds. That is the suite that actually gets used.

Idea 2: mocks encode your beliefs, not the model's behaviour

The tempting shortcut is to fake Bedrock everywhere and pay nothing. It forfeits the entire point, and slice 8 supplied the proof. The check-in composer asks Claude for a structured email through a tool schema that marks sign_off as required. One day the model returned a complete, perfectly good email — without sign_off. Validation rejected it, and a personalized email silently degraded to a generic one.

Tool schema says
required
→
Mock written
from the schema
→
Mock always
includes it
→
Bug invisible
forever

You cannot catch that with a mock, because you wrote the mock from the same schema you misunderstood. A mock encodes the author's belief about the model; the bug lives precisely in the gap between that belief and reality. That gap is what the ~$0.01 bedrock tier buys.

A useful generalisation. required in a tool schema is a hint to the model, not a constraint the API enforces. Validate the fields that make output useful; supply defaults for fields that merely make it polished.

Idea 3: a conditional that has never run is untested code

CareerVault's SAM template contains billing alarms gated behind Condition: IsProd. Only dev had ever been deployed, so CloudFormation had never once evaluated that branch. Everyone assumed it was fine. It looked fine.

A change-set dry run costs nothing, so slice 9 ran one. It failed immediately — and not on the alarms:

→

creates SES identity

The DynamoDB table is named CareerVaultTable-${Environment}. The SES configuration set is named careervault-checkins-${Environment}. But the SES email identity is an email address — and an email address cannot carry an environment suffix. Two stacks in one account therefore fight over it, and the prod stack could never have deployed at all.

Nobody would have discovered that until the day they urgently needed a prod stack.

Idea 4: a requirement can be false and nothing fails

The requirements document promised a tailored résumé "within 30 seconds". Measurement says 72 seconds on a small corpus and about 176 on a real one. Worse, the target was never achievable: API Gateway hard-limits a synchronous request to 29 seconds, which is exactly why the résumé endpoint returns a job id and polls.

A latency requirement and a delivery model are not independent choices. "Within 30 seconds" quietly assumed a synchronous request. Once you exceed the gateway timeout, you are not slightly missing the target — you are in a different architecture. The fix specifies asynchronous, with a ceiling, not merely a bigger number.

The instructive part is why it survived nine slices: nothing fails when a latency requirement is wrong. The résumé still arrives. The user is still happy. The number in the document simply stops meaning anything, silently — the same shape as the check-in tier degrading without a metric.

Idea 5: cost and latency turned out to be one problem

The expensive tier measured its own run, and the number was surprising: $0.113 and 72 seconds, against the 13-entry corpus's $0.35 and 176 seconds. Both runs returned the same REVISE critique verdict and executed the same six phases — so this is not a cheaper code path. The only difference is corpus size.

The agent's retrieval loop re-sends its whole growing message history on every iteration, so both the bill and the wall-clock scale with how much career history you have. Which is the uncomfortable part: CareerVault gets slower and more expensive precisely as it becomes more useful. Two backlog items that had been filed separately — one about cost, one about latency — turn out to be one mechanism viewed from two sides.

Code walkthrough

Roughly 2,000 lines landed, almost all of it tests. Here is the story rather than the file list.

1. The seam that makes local testing possible

Nothing in the application changed to support DynamoDB Local, because the seam was already there:

def get_table():
    global _table
    if _table is None:
        kwargs = {}
        endpoint = os.environ.get("DDB_ENDPOINT_URL")   # ← the whole seam
        if endpoint:
            kwargs["endpoint_url"] = endpoint
        _table = boto3.resource("dynamodb", **kwargs).Table(os.environ["CAREERVAULT_TABLE_NAME"])
    return _table

backend/shared/python/careervault/ddb_helpers.py:34. Set one variable and every helper in the codebase talks to localhost. Note _table is cached — that detail causes a real bug later in this walkthrough.

2. Testing what only a real engine can tell you

The local tier's most valuable file is the one that pins ADR-040. That ADR describes how nested settings updates work, and every claim in it is a claim about the engine. Each was originally established by poking the live table by hand — including one the first draft asserted confidently and got wrong.

def test_seeding_and_writing_in_one_expression_is_rejected_as_overlapping(self, table, user_id):
    table.put_item(Item={"PK": pk_for_user(user_id), "SK": "PROFILE"})

    with pytest.raises(ClientError) as exc:
        table.update_item(
            Key={"PK": pk_for_user(user_id), "SK": "PROFILE"},
            UpdateExpression="SET #s = if_not_exists(#s, :empty), #s.checkin_paused = :v",
            ...
        )

    assert "overlap" in str(exc.value).lower()

tests/integration/local/test_nested_settings.py. DynamoDB refuses an expression naming both a path and its own descendant — "Two document paths overlap with each other". Manual probes do not survive into CI; these do. And DynamoDB Local reproduces both engine rejections faithfully.

3. Testing the deployed stack without a login

The cloud tier needs to call deployed Lambdas as an authenticated user — but Cognito is configured PKCE-only (ExplicitAuthFlows: ALLOW_REFRESH_TOKEN_AUTH), so there is no way to mint a token unattended. Adding one would permanently widen the auth surface to buy a test convenience.

So the tests invoke Lambdas directly, handing them the event shape API Gateway produces after the authorizer has already run:

"requestContext": {
    "authorizer": {"claims": {"sub": user_id, "email": email}},
}
Be precise about what this covers. Real handler code, real environment variables, real DynamoDB, and — most valuably — the real IAM policy attached to each role, which is impossible to test locally and the most likely thing to be wrong after a template edit. It does not cover API Gateway routing, CORS preflight, or the JWT authorizer itself. Stating the boundary is the point; a test whose coverage you cannot describe is a test you cannot trust.

4. Testing a scheduled job that sends real email

The check-in Lambda is the one thing you cannot verify by clicking around the app. It is also dangerous to test: invoking it sends actual email and consumes the user's cycle, because the send slot is claimed before SES is called.

The solution is to split the flow along what is genuinely separable:

Decision half
who is due, slot claim,
cadence, pause
local · $0
→
Compose half
Claude writes the email
bedrock · $0.01
→
Send half
SES delivery
not tested

The decision half — which is the half that actually regressed under manual testing — runs free against DynamoDB Local. The deployed Lambda is invoked too, but only after reading live state and skipping if any real user is due, since _process_user runs only for due users. A no-due run still executes scan_profiles(), which is what exercises the dynamodb:Scan IAM grant. The send half is deliberately untested: a test whose assertion is "an email arrived" is a test nobody can run twice.

5. The frontend gate that proved nothing

CI ran typecheck, build, and lint. None of those execute a component, so a green pipeline proved the code compiled and nothing more. Filling that gap ran straight into a Vitest trap worth knowing about:

A vi.fn() that returns a rejected promise fails the test even when your component catches the rejection correctly. Vitest's spy tracks settlement, and the derived promise chain it attaches for that goes unhandled. Confirmed by bisection: it reproduces with zero assertions in the test body, and vanishes entirely without the module mock.

Every error-path test is unwritable that way. The workaround turned out to be the better design — stub fetch and keep the real API module:

const calls = stubFetch(
  { status: 409, body: { possible_duplicates: [DUPLICATE] } },
  { status: 201, body: { entry: {} } },
);

await user.click(confirmButton());
await user.click(await screen.findByRole("button", { name: /save anyway/i }));

expect(calls[1].body).toMatchObject({ acknowledge_duplicate: true });

Testing at the network boundary puts the API layer's 201/200/409/422/500 mapping under test too, and lets assertions check the actual request body — which is where the backend contract lives. "Save anyway" now verifies the acknowledge flag really goes on the wire.

6. What the code review caught afterwards

An advisory review run after all of the above found fifteen issues in this slice's own test code. Two could have caused real side effects on live data, and both are instructive:

# Before — a single Scan
profiles = live_table.scan(FilterExpression="SK = :sk", ...).get("Items", [])
if any(is_due(p, now) for p in profiles):
    pytest.skip(...)

DynamoDB reads up to 1 MB before applying a filter, and each entry carries a ~1024-float embedding (~20 KB). So that call can return having seen ~50 items and no PROFILE at all — the guard misses a due user, the test invokes anyway, and it sends a real email while advancing the schedule a full cadence. The guard that existed to prevent a side effect could cause one. It now paginates.

The second: settings tests wrote PROFILE rows that were immediately due (the handler stamps the caller's email, and a profile with an email and no next_checkin_at is due now). Cleanup normally removes them, but a Ctrl-C during a 7-minute poll leaves an orphan the daily scheduler bills a model call for, every day. The fix seeds a far-future date before the test writes anything — making the orphan impossible rather than unlikely.

A recurring lesson across the whole slice: several tests written this slice passed for the wrong reason — one asserted a status code the system never emits, one checked "one" in answer (which "someone" satisfies), one compared timestamps formatted to whole seconds so the comparison was always trivially true. The remedy each time was the same: break the thing on purpose and confirm the test notices.
