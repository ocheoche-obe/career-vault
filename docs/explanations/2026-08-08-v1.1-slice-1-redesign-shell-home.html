Background

This slice is the first of v1.1, and on paper it is the least interesting kind of work: make the app look better. CareerVault had been visually basic since slice 4 — logged as B-001, one vague line in the backlog reading "flesh out the UI."

What actually happened is that measuring the app before restyling it turned up two failing requirements nobody knew were failing, and measuring the incoming design turned up two accessibility failures that no amount of looking at it would have revealed. The styling was the easy part. This explainer is about the measuring.

Skippable if you know it: what actually serves this page

CareerVault's frontend is a React + Vite single-page app (ADR-003). It is not served by a server that runs code. The built bundle — one HTML file, one JS file, one CSS file — sits in a private S3 bucket, and CloudFront serves it worldwide with Origin Access Control so the bucket itself is unreachable from the internet (ADR-019).

The two paths are completely separate, and that separation is the reason a frontend-only slice could still surface a backend performance problem: the page renders instantly from CloudFront, and then sits there waiting on the second path.

The one AWS concept this slice turns on: cold starts

Lambda cold start. AWS Lambda does not keep your function running. When a request arrives and no initialised copy exists, AWS must allocate a micro-VM, download your deployment package and layers, start the Python runtime, and execute your module-level code — before your handler runs at all. That is a cold start. Once warm, the same environment is reused for subsequent requests and the overhead disappears. AWS keeps environments warm for an unpublished period, typically minutes to tens of minutes of idleness.

Cold starts are usually filed under "a tax you pay occasionally." The interesting part of this slice is discovering that for CareerVault, that framing is exactly backwards.

What the design handoff was

The redesign came from Claude Design as a bundle of HTML prototypes plus a written specification: a full colour-token table, per-view layouts specified to the pixel, and a state model. It declared itself high-fidelity — "Colors, typography, spacing, radii, and interactions are final."

It is a genuinely careful document. It is also silent on accessibility — no contrast target, no focus states, no ARIA — and that silence turns out to matter.

Intuition

1. The cold path is the typical path

The plan for v1.1 said to enumerate before styling. The obvious reading is "catalogue what's broken in the current UI" — but almost all of that CSS was about to be deleted, so those findings would be bug reports against code that would not exist. The enumeration was retargeted at things that survive a visual rebuild. One of them was simply: how fast is this thing, actually?

Requirement NFR-2.3 says the dashboard loads in under 2 seconds. It had never had a number attached — scored "❓ Unverified" on the MVP scorecard. So we measured it, by driving the real app against the deployed dev API.

Two things fall out immediately. First, the client is not the bottleneck — 3639 of the 3686 milliseconds are the API call. Rendering thirteen entries is free. Second, warm comfortably meets the 2s budget and cold misses it by nearly double.

Here is where most teams would report the average, or the warm number, and move on. That would be wrong here, and the reason is a product fact rather than a technical one.

The insight. CareerVault's entire retention mechanism is FR-4: a scheduled check-in email that nudges you to log accomplishments, on a weekly-to-monthly cadence. The whole point is that you are not using the app in between. So a user arriving from that email has not touched it in a week — and the Lambda is reliably, structurally cold when they do.

The cadence that drives retention also guarantees the slow path. The two features are coupled, and nothing in either one's design says so.

So the cold number is not an edge case to be averaged away — it is the number describing the app's core loop. The scorecard now records NFR-2.3 as "met warm, failed cold," which is less tidy than a tick or a cross and considerably more honest.

2. You cannot see a contrast failure

The second thing worth measuring was the incoming design itself. Every foreground/background token pair was run through the WCAG contrast formula. Almost everything passed comfortably — but two holes appeared, and neither is visible by inspection.

Tokenon bgon surfaceon sunkenon raised
text-secondary #a8a4c08.167.747.997.39✅
text-muted #8b88a85.785.485.655.23✅
text-faint #6f6c883.903.703.823.53❌ needs 4.5
accent #7c6cff5.094.824.984.61✅

WCAG AA requires 4.5:1 for normal text. There is a relaxation to 3:1 for "large" text — but large means 18.66px bold or 24px regular, and the handoff assigns text-faint to eyebrows, timestamps, record numbers and axis labels all specified at 10–11px. The smallest text in the design is also its lowest-contrast text. No exemption applies.

The second hole is worse because it is invisible in a different way. The design says outline: none on inputs, and signals keyboard focus purely by changing the border colour:

resting border
#2b2b46
→
focused border
#4b3fa8

Contrast between the two states: 1.68. The ring against its own input: 2.35, where WCAG 1.4.11 wants 3.0. Keyboard focus is, in practice, unindicated.

The fix is the pleasing part. Neither correction invents a colour — both come out of the handoff's own palette. text-faint is lifted along a single axis (HSL lightness 47.8% → 54.6%, hue and saturation held exactly) to #817e99, the minimum lift that clears 4.5 on all four surfaces. And for focus, the palette already contained something that works: --accent #7c6cff scores at worst 4.61 against every surface. So the ring is a real ring made of an existing token.

Why the minimum lift matters. The deviation is deliberately bounded so that a reviewer can diff the shipped :root block against the handoff's token table and find exactly two differences, both documented in ADR-043. A design that has been reviewed dies by a thousand small implementer preferences; "two values, measured, minimum-magnitude, written down" is what makes a deviation defensible rather than the start of drift.

3. A landmark you lose by nesting

The old shell rendered like this:

<main>
  <header>…</header>      ← inside main
  <nav>…</nav>            ← also inside main
  {the current view}
</main>

That looks harmless. It is not, and the live accessibility tree is precise about why:

- main:
  - generic:                  ← <header> — banner role LOST
    - heading "CareerVault" [level=1]
    - button "Sign out"
  - navigation:               ← <nav> — navigation role SURVIVES
    - button "Chat"
The rule. <nav> maps to the navigation landmark wherever it appears. <header> only maps to banner when it is not a descendant of main, article, aside, nav or section — otherwise it silently degrades to a generic container. One of the two survived the nesting and the other did not, and nothing in the visual rendering differs at all.

This is the category of defect that motivated retargeting the whole enumeration. It is a property of DOM structure, not of styling — so a purely visual redesign would have carried it forward untouched and invisible. The same is true of the other findings: no aria-current on the active tab, no live region anywhere, inputs labelled only by placeholder, and no view owning an <h1>.

That last one had a trap in it. The redesign gives every view its own 30px title styled as <h1> — while keeping the "CareerVault" wordmark, which was the app's only <h1>. Ported naively, every page would have shipped two.

Code walkthrough

The token layer, and one rule that makes it enforceable

frontend/src/index.css was, before this slice, mostly unmodified Vite starter template — #social, .counter, a code {} block, and three asset files referenced nowhere. That is a pleasant discovery when you are about to replace a file: most of it was dead.

It is now the only file in the app permitted to define a colour. That is not a style preference; it is what makes two themes tractable:

A raw hex in a feature stylesheet is a light-mode bug that dark-mode review cannot see. If chat.css hard-codes #f5f3ff, it looks perfect in dark mode and is invisible-on-white in light mode — and you will only find out by switching themes on every view. Making "no hex outside index.css" a slice exit criterion turns a class of bug into a grep.

The theme structure inverts the usual convention, deliberately (ADR-044):

:root { /* the handoff's DARK tokens, verbatim except ADR-043's two */ }

@media (prefers-color-scheme: light) {
  :root { /* derived light tokens */ }
}

Light-first is more common. Dark sits on bare :root here for two reasons: the dark palette is the approved artifact, so its values sit unqualified where they can be diffed line-by-line against the handoff's table; and a browser that cannot resolve prefers-color-scheme falls back to the design as approved rather than to our derivation.

The light palette is derived, not supplied — the handoff ships one palette and it is dark. Most of it transfers structurally (in both themes "elevated" is lighter than the page, "sunken" is darker than its card). One thing does not:

/* dark: intensity reads as BRIGHTER */
--heat-0: #1a1a2c;  →  --heat-4: #a58cff;

/* light: intensity must read as DEEPER, or an empty
   week becomes the loudest cell on the page */
--heat-0: #eae7f6;  →  --heat-4: #5b45c4;

The compatibility shim, and why it had to exist

This slice redesigns the shell and Home; five views keep their old stylesheets until slice 2. Those stylesheets reference old token names — --text-h, --text, --accent-bg. And here is the trap:

An unset CSS custom property resolves to nothing, not to a fallback. color: var(--text-h) where --text-h no longer exists does not fall back to a sensible default — the declaration is invalid at computed-value time and the property inherits or resets. Deleting the old names outright would have rendered five views essentially colourless, in both themes.

So index.css carries five aliases, loudly marked as temporary. Each dies with the stylesheet that uses it; when the block is empty, slice 2 is done.

The shell

frontend/src/App.tsx now renders <header> and <nav> as siblings of <main>, so the banner landmark exists at all. The wordmark became a <span>, freeing each view to own the page's single <h1>. The active tab carries aria-current="page", so the state is in the accessibility tree and not only in a CSS class.

Two things the handoff did not account for, both preserved deliberately:

  • Sign-out. The design shows a bare avatar and no sign-out control anywhere. Losing a functional control to visual fidelity is not a trade worth making, so the avatar became a <details> disclosure holding the email and the sign-out button.
  • The mobile overflow fix. This is the same change. NFR-6.2 was failing on all five views — 82px of horizontal overflow at 360px — and the cause was entirely shell-local: .app-header was width: min(720px, 100%) carrying a 241px email string that cannot compress, beside a nav that neither wrapped nor scrolled. Moving the email into a fixed-width disclosure and letting the nav scroll fixed every view at once. Now 0px on all six.

Deriving Home, and defining a word

frontend/src/lib/aggregates.ts computes everything Home displays from the entry list the shell already fetched — no new endpoint, no schema change, $0 added cost (ADR-045). Promotion to a server-side aggregate is tracked as B-029 with an explicit trigger, and the component's props are designed not to change when it happens.

The interesting part is that the design invented a concept the data model does not have: a streak. Defining it is a product decision, so it lives in the ADR rather than in whichever component happened to implement it. Three rules do the work:

// 1. created_at, NEVER event_date
function loggedAt(entry) { return new Date(entry.created_at) }

A streak measures the habit of logging. Counting event dates would let you backfill a 2019 job and extend a 2026 streak — which inverts the metric from "how consistent are you" into "how long is your career."

// 2. the current period is neutral until it ends
let cursor = logged.has(currentPeriod) ? currentPeriod : currentPeriod - 1;
while (logged.has(cursor)) { current += 1; cursor -= 1; }

An unfinished period with no entry is not a miss. Without this, every user's streak reads zero every Monday morning until they log something.

// 3. periods anchored to the calendar, not to "now"
case "weekly": return Math.floor(mondayOf(d) / WEEK_MS);

A rolling window measured back from the current instant would make the number drift day to day with no user action. Period length comes from the same cadence table that paces the check-in emails, so the streak can never disagree with the thing that prompts it.

Where the design was amended

Two elements did not survive contact with the real app. The handoff specified the year-activity grid as 130 cells in 26 fortnight columns — which measures 442px inside a ~1172px card, rendering as a small dense block with two thirds of its card empty. It also could not fit a mobile viewport, and the ~2.8-day bucket it implied meant nothing.

Rebuilt as one cell per day across 53 week-columns × 7 day-of-week rows — the GitHub contribution-graph form. 1fr columns fill any width honestly, and it earns a property the fortnight buckets could not:

Because rows are fixed weekdays, a user who checks in every Friday produces a clean horizontal band. The chart shows the cadence — which is the entire point of Home. The original bucketing was structurally incapable of showing that.

The second amendment: the big stat numerals moved from JetBrains Mono to Figtree with tabular-nums. Mono is right for small data-chrome and keeps its job on dates and micro-labels — but at 30px it was the largest type on the page, and a heavy coding face beside a soft grotesque functions as a second display typeface. That is exactly what the handoff itself set out to avoid when it dropped concept 1d's serif accent for "one sans across the entire UI." Following the letter of the spec would have worked against its stated intent.

What the code review caught that browser testing did not

Worth recording honestly. The diff had been driven in a real browser at two viewports and two themes before review. The review still returned eight findings, and the most severe was a layout regression on five of six views: making <main> a plain block removed the flex centring those un-redesigned views silently depended on, so they rendered flush against the left edge under the sticky header.

The generalisable lesson. Browser verification confirmed the views that were built and never re-checked the ones merely touched. When a change lands in a shared container, the blast radius is every child — and "I looked at it" only ever covers what was on screen.

All eight were fixed in-slice, including an unguarded Intl.format call that would throw a RangeError and white-screen the entire app on a single malformed date, since there is no error boundary above Home.

Quiz

The dashboard loads in ~940ms warm and 3686ms cold, against a 2-second requirement. Why does the slice report the cold number as the one that matters, rather than the warm average?

The design specifies <code>text-faint</code> #6f6c88, which scores 3.53–3.90 against the four surface colours. WCAG AA allows 3:1 for large text. Why doesn't that exemption rescue it?

The old shell rendered <code>&lt;header&gt;</code> and <code>&lt;nav&gt;</code> inside <code>&lt;main&gt;</code>. What did the live accessibility tree show?

ADR-045 specifies that the streak counts <code>created_at</code> and never <code>event_date</code>. What breaks if you use <code>event_date</code>?

Why did deleting the old token names outright require a compatibility shim rather than just letting the un-redesigned views fall back?
