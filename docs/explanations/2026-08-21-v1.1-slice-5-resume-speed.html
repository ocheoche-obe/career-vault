Background

This slice is about making the résumé generator faster and cheaper. But the interesting part is not the 41% — it is that the change we built the slice around was not the one that worked, and we only know that because we measured properly. Everything below is in service of that story.

Skippable if you know AWS: what the pieces are

Lambda runs your code without a server. When a request arrives and no container is already running your function, AWS creates one: downloads your code, starts a Python interpreter, imports your modules. That is a cold start, and it is billed and reported separately from the actual work. Once warm, a container is reused for later requests until it is reclaimed.

Amazon Bedrock is AWS's managed access to foundation models. CareerVault talks to it through the Converse API, a single chat-shaped interface that works across model vendors. Every response carries a usage block: how many input tokens you sent, how many output tokens came back. You are billed on both, at different rates, and output is roughly 5× the price of input.

Prompt caching is a Bedrock feature that lets you mark a point in your prompt and say "everything before here is stable — remember it." Subsequent calls that share that exact prefix read it from cache instead of re-transmitting it, at about a tenth of the input price. Writing the cache costs slightly more than a normal input token (1.25×), so caching only pays if the prefix is actually re-read.

Cross-cloud parallel. Azure OpenAI does this automatically for prefixes over 1024 tokens with no API surface at all — you cannot control placement, you just observe cached_tokens in the response. Google Vertex AI splits it in two: implicit caching that behaves like Azure's, and explicit CachedContent objects you create, name, give a TTL, and reference by ID. Bedrock sits in between — you place the breakpoint inline with cachePoint markers, but you do not manage a cache object's lifecycle.

The narrow background: what the résumé agent does

Generating a tailored résumé is CareerVault's most expensive operation and its slowest. It is a six-phase agent loop (ADR-010 — we own the loop rather than using Bedrock Agents, deliberately, for the learning value):

Phase 2 is the only one that repeats. The model calls search tools, gets results back, and decides whether to search again — up to 8 times. Each iteration re-sends the entire conversation so far, because that is how a stateless chat API works: there is no server-side session, so "remember what we discussed" means "send it all again."

That re-send is logged in the backlog twice, from two angles: B-004 calls it the dominant cost driver, B-020 calls it the dominant latency driver. The backlog describes them as "one mechanism seen from two sides." Hold that thought — it turns out to be half true, and the half that is false is what this slice discovered.

The whole run is asynchronous (ADR-037): a real run takes 1–3 minutes, and API Gateway hard-caps an integration at 29 seconds, so the request returns a run_id immediately and a self-invoked worker Lambda does the work while the browser polls for status.

Intuition

Rule one: measure before you optimise

CareerVault has three latency requirements. Before this slice, none of them had a number. Not "a number we were failing" — no number at all, for nine slices.

The reason is worth naming, because it generalises. Cost has a forcing function: a bill arrives monthly and somebody reads it. Latency has none. Nobody gets an email saying your dashboard got slower. So per-turn cost was known to four decimal places ($0.006 for a chat turn) while latency went entirely unmeasured.

So the first thing built was not an optimisation. It was an instrument (ADR-047): every integration test run now prints a timing table.

The design decision that matters: the harness records everything and asserts almost nothing. Tests fail only against a ceiling set far above the requirement. Why? Because one of these NFRs fails today. Gating on the requirement itself would ship a suite that is permanently red — and a suite that is always red tells you nothing when it goes red for a new reason. The requirement verdict is a human reading numbers; the assertion only catches drift.

What the instrument found on its first run

The dashboard-load requirement (NFR-2.3, ≤ 2 seconds) was known to be failing, and the backlog had a confident explanation: B-013. Every career entry is stored with a 1024-dimension embedding vector (~20 KB), and the read fetches all of them just to throw them away. Obviously that is the problem. Obviously.

Measuring it decomposed the number instead of assuming it:

TermColdWarm
Container init (Init Duration)1,053 ms—
Handler execution778 ms193 ms
Handler, empty corpus—6 ms
Observed round trip2,620 ms ❌300 ms ✅

Subtract the empty-corpus handler (6 ms) from the 13-entry handler (193 ms) and you get the part that actually scales with the corpus: ~188 ms, about 14.5 ms per entry. That is roughly 8% of a cold dashboard load.

This is the whole argument for measuring. The "obvious" fix — project the embedding out of the query — would have bought about 190 ms against a 2,300 ms problem, roughly 7%, and been written up as addressing the requirement. The real cause is cold start: 1,053 ms of container init plus ~580 ms of first-invocation setup inside the handler. B-013 is real and it does scale — the read alone hits the 2-second budget somewhere near 140 entries — but it is not what breaks the requirement today. Both the ADR and the backlog entry were corrected in place.

The thing live AWS contradicted: a cache that silently does nothing

Before writing the caching ADR, we probed the actual API rather than trusting the docs. Same request shape, two models:

ProbeWhat usage came back
Sonnet 4-6, ~2.4K-token prefixcacheWriteInputTokens: 2403, then cacheReadInputTokens: 2403 ✅
Haiku 4.5, identical prefixcacheWrite: 0, cacheRead: 0, inputTokens: 2415 — billed in full
Haiku 4.5, ~9.6K prefixcacheWrite: 9602 — so Haiku does support it

Bisecting put Haiku's minimum near 4096 tokens, against Sonnet's 1024. Below the minimum, Bedrock does not error. It does not warn. It accepts your cachePoint, ignores it, and charges full price.

So "we added caching" and "caching happened" are two different claims, and only the second one saves money. This is the third time this codebase has hit the same shape: ADR-021 found that required in a Converse tool schema is a hint the model may ignore; ADR-014 had to be corrected when "browser-side" turned out to describe the Web Speech API but not where the audio is processed. The house rule that came out of it: on Bedrock, verify the effect, never the request.

Where to put the breakpoints

Caching only pays where a prefix is re-read. A one-shot call that caches its prefix pays the 1.25× write premium and never gets the 0.1× read back — a pure loss. So caching goes on the retrieval loop and nowhere else. Two breakpoints: one after the system prompt (stable forever), and one that moves to the end of the conversation on each iteration.

Iteration 2 sends:

[ system prompt + tool schemas ] ◄── breakpoint 1, cached since iteration 1
[ initial user prompt ]
[ assistant: call search_entries ]
[ user: tool results ]         ◄── breakpoint 2 moves here

Iteration 3 reads all of the above from cache at 0.1× and writes the new turn.

Old breakpoints are stripped before the new one is added, because Claude allows only a few of them. That is safe: a cachePoint is a marker, not content, so removing one does not change the token prefix the cache is keyed on.

The result, and the twist

Two levers shipped together — caching, and moving the critique phase from Sonnet to the much cheaper Haiku. Measuring both together would have been enough to claim a win. Measuring them separately cost one extra $0.08 run and changed the conclusion entirely:

ConfigurationWall clockCost
Baseline81.8 s$0.1233
Caching only84.2 s$0.1071
Caching + Haiku critique48.4 s$0.0785

Prompt caching bought about 13% of the cost and none of the latency. 84.2 s against an 81.8 s baseline is inside the run-to-run noise (two baseline runs measured 79.2 s and 81.8 s). The critique swap — ranked as the minor lever, almost an afterthought — delivered the entire 43% latency win.

Why, in hindsight. The reasoning went: B-004 and B-020 are "one mechanism seen from two sides," we are attacking that mechanism, so both should move. But a run's wall clock is dominated by output token generation across draft, critique and revise — and caching does nothing whatsoever to output. Cheaper input, identical generation time. The two backlog items really are one mechanism for cost. For the clock they are not, and nothing in the argument distinguished them.

Caching stayed. The test fixture has 2 entries; the real corpus has 13 and runs ~83K tokens against this fixture's ~21K, and caching scales with the size of the re-sent prefix. What changed is the claim, not the code.

Making the wait feel shorter, honestly

The last piece attacks perceived time rather than real time. The draft exists at around T+60s but was withheld until critique and revise finished. Now the worker publishes it as a non-terminal draft_ready poll state (an ADR-037 amendment):

pending
→
draft_ready
~T+60s, shows a draft
→
completed
…or from either state →
failed

Three things it deliberately does not do: no S3 artifacts, no presigned URLs, and no durable RESUME# history record. ADR-046's rule is that "past résumés" means résumés that exist, and a draft nobody has critiqued is not one. Nothing is downloadable, and a run can still end failed after showing a draft — so the UI labels it as unfinished rather than presenting it as the résumé.

Code walkthrough

1. Teaching the shared client to speak in blocks

The shared Bedrock wrapper took system as a plain string and wrapped it itself, so a cachePoint was not expressible at all. It now accepts either (backend/shared/python/careervault/bedrock_client.py:138):

request["system"] = [{"text": system}] if isinstance(system, str) else system

Every existing caller passes a string and is unaffected. The docstring carries the warning about per-model minimums, because that is where someone reaching for this feature will look.

2. Placing the breakpoints

Two small helpers in backend/functions/resume_agent/agent.py:225. The interesting one is the moving breakpoint:

def _with_moving_breakpoint(messages: list[dict]) -> list[dict]:
    cleaned = []
    for message in messages:
        content = [b for b in message["content"] if "cachePoint" not in b]
        cleaned.append({**message, "content": content})
    if cleaned:
        cleaned[-1] = {**cleaned[-1],
                       "content": [*cleaned[-1]["content"], _cache_point()]}
    return cleaned

Note it builds new dicts rather than mutating. The loop reuses its messages list across iterations, so mutating in place would compound a breakpoint per turn into the caller's own history — and there is a unit test that fails if you do.

3. Getting the arithmetic right

Cache tokens are billed at different rates and reported separately — inputTokens excludes anything served from or written to cache. We verified that against a live response rather than assuming it (a 2403-token cached prefix returns inputTokens: 13), because guessing wrong in either direction silently corrupts every cost number the app reports:

return (
    input_tokens * in_rate
    + cache_write_tokens * in_rate * 1.25   # writes cost a premium
    + cache_read_tokens  * in_rate * 0.10   # reads are a tenth
    + output_tokens * out_rate
)

The budget ceiling still counts cache tokens at face value, deliberately. That ceiling bounds context size, not spend — a run whose prompt has ballooned is out of control whether or not the growth was cheap.

4. The draft escapes without the agent learning about DynamoDB

run_agent gained one optional parameter, and the handler supplies the callback (backend/functions/resume_agent/handler.py:341). This preserves something ADR-037 called out as a win: the agent module is a pure function of its inputs, which is why async was a pure wiring concern with no loop rework. Teaching the loop to write to DynamoDB would have spent that.

draft = _draft(run, requirements, retrieved)
if on_draft is not None:
    try:
        on_draft(draft)
    except Exception:
        logger.exception("on_draft callback failed; continuing the run")

The swallow is the point: losing a progress signal is not a reason to lose the résumé.

5. The frontend bug worth the whole walkthrough

The first version stored the draft on the component's stage object. The poll effect lists stage in its dependency array. So every poll produced a new stage object, React tore the effect down and re-ran it, and re-running it polls immediately instead of after the 3-second timer.

poll returns draft
→
setStage(...)
→
effect re-runs
→
poll immediately
↺ measured at 18,445 requests in 1.5 seconds, for the ~60s a real run spends here

The fix is to keep the draft in state the effect does not depend on (frontend/src/resume/Resume.tsx:97). What makes this a good teaching case is the test:

const afterDraft = calls.length;
await new Promise((r) => setTimeout(r, 1_000));
expect(calls.length - afterDraft).toBeLessThan(5);

It asserts a request count over elapsed time, because that is the only thing that distinguishes the bug from correct behaviour — the rendered output is identical either way. A snapshot test, an accessibility assertion, a "does the draft appear" test: all of them pass on the broken version.

6. What the harness had to get right about itself

Two bugs in the measuring instrument, both of the same family — a number that looks like evidence and is not:

  • Medians taken per column, not per sample. Taking the median observed time and the median Lambda duration independently produced a row where the round trip was shorter than the work it supposedly contained, because the two numbers came from different calls. Fixed by picking one representative sample and reporting it whole.
  • A latency test with no correctness assertion measures an unknown operation. This bit twice. A misspelled field name (issue_date for issued_date) made the handler return 422 in 2 ms — recorded as a beautifully fast ingestion. Then the repeats posted identical text, so the duplicate check (ADR-033) answered 409 before the database write, and a 239 ms "confirm write" number reached the project scorecard describing a rejection. Both now assert the status code, so a regression fails the suite instead of publishing a flattering number.

7. Forcing a cold start without touching anything

Cold starts cannot be produced by calling something repeatedly — repetition is exactly what warms it. And the honest signal is not wall clock: a slow first call could be a cold Lambda or a cold boto3 client resolving credentials and doing a TLS handshake, and those have unrelated fixes. So the harness reads Lambda's own REPORT line, where Init Duration appears only on a cold start, and forces one with a concurrent burst up to the function's reserved-concurrency cap. Nothing is mutated. It is opportunistic by nature — once the container pool is warm, no burst can force one — so a miss records a "not captured" row rather than quietly vanishing from the table.
