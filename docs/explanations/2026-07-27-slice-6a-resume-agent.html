Background

Slice 6a is where CareerVault stops being a filing cabinet and starts being the thing it was built for: you paste in a job description, and a few minutes later a tailored résumé PDF is waiting for you. Everything before this slice — the chat capture, the entries dashboard, the résumé upload bootstrap — existed to fill the vault. This slice spends it.

It is also, by a wide margin, the most intricate thing in the codebase: 3,150 added lines across 28 files, a new Lambda layer built inside Docker, a new IAM shape, and a control flow that loops under three simultaneous budgets. So it's worth building up to it slowly.

Deep background — skip if you already know AWS serverless and Bedrock tool use

Five ideas carry almost all the weight in this slice.

A Lambda function is a chunk of code AWS runs for you on demand. You don't manage a server; you hand AWS a zip file, an entrypoint, a memory size, and a timeout, and it invokes your entrypoint whenever something triggers it. Two properties matter here. First, the timeout is a hard wall — CareerVault's résumé function is configured for 300 seconds, and at 300 seconds the execution is killed mid-sentence. Second, a Lambda can be invoked synchronously (the caller waits for the return value) or asynchronously (AWS accepts the payload, returns immediately, and runs your code detached from the caller). That second mode is the hinge this whole slice turns on.

A Lambda layer is a zip of shared files that AWS mounts into the function's filesystem at /opt/ before your code runs. CareerVault already had one (careervault-shared, mounted at /opt/python/, holding the Pydantic models and AWS helpers every function imports). This slice adds a second one, and it's a different animal: WeasyPrint, the HTML-to-PDF renderer, needs native C libraries (Pango, Cairo, GDK-PixBuf) compiled for the exact CPU architecture and Linux the Lambda runs on. You cannot pip install your way there from a Mac. The layer is built inside a Docker container that mimics the Lambda runtime, which is why infrastructure/weasyprint-layer/ has a Makefile rather than just a requirements.txt.

API Gateway's 29-second ceiling. CareerVault's HTTP front door is API Gateway (REST), which forwards each request to a Lambda and waits for the answer. It will not wait longer than 29 seconds. That number is not a suggestion and, in practice, not negotiable. Remember it — it is the single constraint that reshaped this slice's design.

Amazon Bedrock is AWS's managed API for foundation models. CareerVault talks to it through the Converse API, which takes a list of messages and returns the model's reply along with a usage block counting input and output tokens. Those token counts are the project's cost telemetry, and they matter more here than anywhere else: this is a $5/month project, and this one feature is the dominant spender.

Tool use is the idea that makes an "agent" possible. You hand the model a list of tools — each a name, a description, and a JSON Schema for its inputs — and instead of replying with prose, the model can reply with a structured request: call search_entries with {"query": "infrastructure as code"}. The model cannot run anything; it can only ask. Your code executes the tool, appends the result to the conversation, and calls the model again. That request/execute/reply cycle, repeated, is the agent loop. Converse also lets you force a specific tool via toolChoice, which turns tool use into a reliable structured-output mechanism — the model must answer in the shape of your schema.

Embeddings and cosine similarity. An embedding model (here, Amazon Titan Text Embeddings v2) turns a piece of text into a list of ~1,024 numbers positioned so that texts with similar meaning land near each other. "Migrated the billing service to Terraform" and "infrastructure as code" are not string matches, but their vectors point in nearly the same direction. Cosine similarity measures that angle, returning roughly 1.0 for "about the same thing" and 0.0 for unrelated. CareerVault embeds every entry when you save it and stores the vector on the entry item itself.

Intuition

Start with the naive version, because it clarifies what the real design is buying. You could write this feature in about forty lines: read all of the user's entries, paste them and the job description into one enormous prompt, and ask a model for a résumé. That works, in the sense that output appears.

What it doesn't do is any of the things a person actually does when tailoring a résumé. A person reads the job description and works out what it's really asking for. They go looking through their history for evidence of each of those things, and they notice when they've found nothing for one of them and go hunting differently. They write a draft. Then they reread it as if they were the hiring manager, wince, and fix it. The six-phase loop is that sequence, made explicit:

Phases 4 and 5 form a small cycle: critique the draft, revise it, critique again. Phase 6 is deliberately outside the intelligence entirely.

Two kinds of tools, and why that distinction is the whole design

The agent hands Bedrock two families of tools that look identical on the wire and do completely different jobs.

Action toolsStructured-output tools
Whichsearch_entries, get_entry, list_skills, retrieval_doneextract_requirements, submit_resume, submit_critique
toolChoiceauto — the model decides what to call and when to stopforced to one named tool — the model has no choice
What a call means"please run this for me""here is my answer, in your schema"
Who actsthe Lambda executes it and feeds the result back nothing is executed; the payload is the output
Validationloose — the Lambda reads the few fields it needs a Pydantic model is the gate

That split is what people mean by "tool use as a control plane." The forced tools give you structured output you can validate. The auto tools give the model the steering wheel — it decides how many searches to run, whether a snippet is worth expanding, and when it has enough. Your code's job stops being "orchestrate the steps" and becomes "offer capabilities and enforce limits."

Retrieval, with toy data

Suppose the target is "Senior Cloud Engineer — AWS, infrastructure as code, serverless, mentoring." Phase 1 sends it to Haiku (cheap, and this is decomposition, not judgment) with extract_requirements forced. Out comes:

{
  "target_type": "JD",
  "requirements": ["AWS production experience", "Infrastructure as code",
                   "Serverless architecture", "Mentoring engineers"],
  "sub_queries": ["AWS production ownership", "Terraform / CloudFormation work",
                  "Lambda and event-driven systems", "mentoring and onboarding"]
}
Why sub-queries, not one query? Embedding the whole job description gives you one vector that is the average of four different topics — and an average points somewhere none of them are. Four focused vectors each find their own matches. This is query expansion, and it's the reason Phase 1 exists as a separate phase at all.

Phase 2 hands those to Sonnet with the four action tools and toolChoice: auto. The model calls search_entries with the first sub-query. The Lambda embeds that phrase with Titan, cosine-scores it against every entry it loaded up front, and returns the top matches as compact snippets:

entry_idtypetitlesimilarity
01HQ…7FJOBPlatform Engineer, Northwind0.71
01HR…2KPROJECTTerraform migration of billing stack0.68
01HS…9CMILESTONECut deploy time 40 min → 6 min0.55

Now the interesting part: the model reads those, notices that the "mentoring" requirement has no evidence yet, and issues a search the Lambda never planned — maybe "onboarding junior engineers" or "led a study group". If a snippet looks central it calls get_entry for the full text. When further searching would be redundant it calls retrieval_done, and the loop exits. That adaptivity is the entire argument for an agent over a pipeline.

Phase 3 then gets the retrieved entries and a blunt instruction: every employer, institution, credential, and date must come from these entries; if the material is thin for a requirement, omit it rather than invent. That prompt is the primary defense against a résumé that lies about you — the Pydantic model checks shape, not truth.

Three budgets, always running

An unbounded agent is a billing incident. This one runs under three simultaneous limits, plus two behavioral guards:

The two red boxes are worth a second look, because they're the ones that address how models actually misbehave. A model that has run out of ideas doesn't crash — it repeats itself. So the third time it makes a byte-identical tool call, the Lambda appends a line to the tool result: "You have already made this exact call. Use the results you have or try a different tool." It's a nudge inside the data, not a block. Similarly, if a second critique lists 80% the same missing requirements as the first, revising again is buying nothing, so the loop stops and finalizes. Both are cheaper than the alternative: paying Sonnet to fail the same way twice.

The 29-second wall

A real run takes 40–120 seconds — the measured one is about 176. API Gateway hangs up at 29. The Lambda behind it doesn't stop when the socket closes; it keeps running and keeps billing, and the browser gets a 504 for a résumé that was successfully generated and then thrown away. That is the worst possible failure: full cost, no product.

So generation became an asynchronous job (ADR-037), and the shape is worth internalizing because it recurs everywhere in serverless:

The POST does the fast, cheap work — validate, check the user actually has entries, write a pending record, hand the job off — and returns a run_id. The worker is the same Lambda function invoked asynchronously with a different payload shape; it runs detached, bounded only by the 300-second function timeout. When it finishes it overwrites the job record with completed or failed. The browser polls GET until one of those appears.

No new entity was needed. The RESUMERUN# item already existed in the architecture as the run trace (what the agent did, what it cost, kept 30 days via a TTL). ADR-037 noticed that a trace with a status field is a job record, and reused it. Polling is a single GetItem.

Phase 6 is deliberately stupid

The last phase has no model in it at all. A validated ResumeDocument goes through one Jinja2 template to HTML; WeasyPrint turns that HTML into PDF; both go to S3. The preview you see in the browser and the PDF you download are the same HTML, so they cannot drift (ADR-018).

One detail rewards attention. Your name, email, and phone are not taken from the model's output — they're read from your profile and passed to the template separately. There is no upside to a language model rephrasing your phone number, and considerable downside. Identity is deterministic; the writing is the agent's job.

Where live AWS corrected the docs

This project treats the architecture document as authoritative until live AWS says otherwise, and then corrects the document rather than quietly coding around it. Slice 6a produced three such corrections, and they're the most instructive part of the diff.

Sonnet 5 is not grantable on this account

ADR-036 chose Claude Sonnet 5, reasoning that the résumé is the payoff feature and deserves the most capable model. The first deployed run failed at the Phase 2 call:

AccessDeniedException: anthropic.claude-sonnet-5 is not available for this
account. ... contact AWS Sales

The diagnosis matters. This was not an IAM problem — Phase 1 on Haiku had just succeeded using the same execution role, which rules out the policy. And it was not the ordinary "enable this model" toggle in the Bedrock console; the wording is account-tier gating. Probing the account showed us.anthropic.claude-sonnet-4-6 and 4-5 both accessible, sonnet-5 denied. The ADR had already written its own escape hatch — "a model swap is a one-line env + IAM change" — so the fix was flipping two CloudFormation parameters to Sonnet 4-6, the newest accessible Sonnet. The IAM shape is identical because both models are INFERENCE_PROFILE-only with the same three-region fan-out.

Inference profiles, briefly. Current Claude models on Bedrock advertise inferenceTypesSupported: ["INFERENCE_PROFILE"] and no ON_DEMAND. You don't invoke the model ID directly — you invoke a profile like us.anthropic.claude-sonnet-4-6 that load-balances across us-east-1, us-east-2, and us-west-2. The practical consequence is that IAM must grant two resource shapes: the profile ARN, and the underlying foundation-model ARN in every region the profile can route to. Grant only the profile and you get a confusing denial from a region you never named.

The architecture's synchronous sequence diagram was wrong

Architecture §3.2.1 showed POST /resumes/generate returning 201 {html_url, pdf_url} synchronously, with §3.2.2 targeting "under 90 seconds." Those two statements can't both hold behind a 29-second API Gateway integration. ADR-037 corrects the document and rejects the tempting workarounds explicitly: Step Functions (heavier infra, and it pulls the loop out of the Lambda, defeating ADR-010's stated learning goal), a quota increase (rarely approaches 120s, and still blocks a browser for two minutes), and cutting the run under 29 seconds (guts the reasoning quality that is the point).

The loop caps were tuned by measurement, not taste

The architecture pinned 15 retrieval iterations and 2 revisions. The first successful live run measured 85K tokens, ~$0.39, ~230 seconds on a 13-entry corpus — functional, but roughly twice the estimate, uncomfortably close to the 240-second budget, and only ~12 runs per $5 month. Two observations from the trace drove the tune-down: retrieval converged in about five iterations (so 15 was never the binding constraint), and the second revision pass never flipped the critique verdict. New defaults: 8 iterations, 1 revision, which brought a run to ~70K tokens / $0.31 / ~176 seconds.

Code walkthrough

Read the diff in this order and it tells a story: first the vocabulary the agent thinks in, then the brain, then the wiring, then the parts that never think at all.

1. The contract — pydantic_models/resume.py (+383)

Four Pydantic models (RequirementsAnalysis, ResumeDocument, Critique, and their nested items) and three functions that build Converse toolConfig blocks. The _forced() helper is three lines and does the heavy lifting: it emits a config with exactly one tool and toolChoice: {"tool": {"name": …}}, which is how "structured output" is spelled in Converse.

Two decisions here are documented in the module docstring and worth understanding:

  • The JSON schemas are hand-written rather than derived from the Pydantic models — which is the opposite of what tools.py does for propose_entry. The reasoning is a genuine distinction, not inconsistency: propose_entry is a shared contract (chat and the upload parser must validate identically, so a single derived source is load-bearing), whereas these schemas are agent-only. And ResumeDocument nests — Pydantic renders nesting as $defs/$ref, which is more than you want to hand a model. The Pydantic model remains the validation authority, so if the hand-written schema drifts, the failure mode is a validation retry, never a bad write.
  • extra="ignore", not "forbid". A generative payload that includes one stray field should drop it, not fail the whole draft.

2. The brain — agent.py (+642)

The module's defining property is stated in its first paragraph: it performs no DynamoDB writes and no S3 or PDF work. It's a pure function of its inputs, which is why the unit tests can exercise the whole loop by faking one module (bedrock_client) and why making generation asynchronous required no changes to it at all.

Every Bedrock call goes through one wrapper, _converse(), which is where metering, tracing, and budget enforcement live together:

run.cumulative_tokens += in_tok + out_tok
run.cumulative_cost_usd += _cost(model_id, in_tok, out_tok)
run.trace.append({...})   # phase, model, stop_reason, tokens, running cost
_enforce_budget(run)      # ← note: AFTER recording

The ordering is deliberate and the docstring calls it out: the call that crosses the ceiling has already been paid for and its result is still used. The guard stops the next call. You cannot un-spend a token, so the honest design is to let the overshoot happen once and then halt.

The phases then read almost linearly:

  • _analyze() — one forced Haiku call. If it fails validation, that's the Phase 1→2 checkpoint: with no requirements there is nothing to retrieve on, so it aborts rather than flailing.
  • _retrieve() — the loop. Call Sonnet, append the assistant turn, and if stopReason == "tool_use", execute each requested tool and append the results as a user turn. Exits on retrieval_done, on any other stop reason, or on the iteration cap. Note the small touch of injecting iterations_remaining into every tool result — the model is told how much rope it has left.
  • _search_entries() — embeds the query, ranks the pre-loaded corpus, returns 300-character snippets. When the Titan call fails it returns {"error": "transient_failure", "retry_advised": true} as a tool result. A tool failure is data the agent can route around, not an exception that kills the run.
  • _structured_resume_call() — shared by draft and revise. Forced submit_resume, and on a validation failure it appends the Pydantic error text to the conversation and asks for a corrected emission. Twice failing aborts the run.
  • _critique_revise() — the small cycle, with four distinct exits: verdict PASS, revisions exhausted, stagnation detected, or an uncritiquable response.
Two asymmetric failure policies. A double validation failure on submit_resume aborts the run — there is no résumé without a résumé. A double failure on submit_critique returns None, and the loop finalizes the current draft. An un-critiqued résumé beats no résumé. The severity of a component's failure is a design decision, not a property of the component.

The bottom of run_agent() is the other half of that philosophy. Four expected terminations — budget, timeout, validation abort, empty retrieval — are caught and turned into a status string on the returned result, with the partial trace attached. Only a genuinely unexpected BedrockError propagates. The caller therefore has one uniform thing to persist and map to an HTTP response.

3. The three-hatted handler — handler.py (+356)

One Lambda, three roles, and the very first line of handler() is the discriminator:

if isinstance(event, dict) and event.get("job") == _WORKER_JOB:
    return _run_worker(event)

An API Gateway proxy event never contains {"job": "resume"}, so that single check cleanly separates the async worker path from the two HTTP paths. Everything below it is ordinary request handling: extract the user ID from the JWT claims (never from the body), branch on method.

_start() is worth reading closely for its ordering. It validates the target, then runs the empty-corpus check before minting a run or spending anything — a user with no entries gets a 400 and a suggestion, not a $0.31 lesson. Then it writes the pending item, self-invokes with InvocationType="Event", and returns 202. If the self-invoke itself fails, it flips the record to failed rather than leaving a job pending forever.

_status() presigns fresh one-hour S3 URLs on every poll from the stored keys, rather than persisting URLs in the item. Persisted URLs would expire while the record lives on for 30 days; keys don't expire. It also maps failure details to human sentences — budget_exceeded becomes "Generation budget exceeded — try a more focused target."

4. The parts with no intelligence — rendering.py (+51) and the template (+139)

Small, and two details carry all of it. autoescape=True is set unconditionally, with a comment explaining why the usual select_autoescape would silently fail here: it keys off the file extension, and .j2 isn't in its list. Since every value in this template is LLM- or user-derived, unconditional escaping is both simpler and safer. And WeasyPrint is imported inside render_pdf() rather than at module top, so the module imports cleanly in the test environment where the layer's native Pango/Cairo libraries don't exist.

5. Shared-layer changes — small, but load-bearing

  • ddb_helpers.py gains three functions. create_resume_run() goes through the SK-prefix-scoped writer with attribute_not_exists(SK); finalize_resume_run() is an unconditional overwrite (by definition the item exists) but still asserts the RESUMERUN# prefix in code; get_resume_run() is the polling read. That prefix assertion is defense in depth — a bug that constructed the wrong SK cannot silently overwrite an entry.
  • bedrock_client.py now catches ReadTimeoutError and ConnectTimeoutError alongside ClientError. A socket timeout is not a ClientError, so previously it would have escaped uncaught — and the agent's long Sonnet generations are exactly the calls most likely to brush a read timeout. The refactor pulls the backoff into _backoff_sleep() so both paths share exponential backoff with full jitter.

6. Infrastructure — template.yaml (+195) and the WeasyPrint layer

The function gets 1536 MB (memory buys proportional CPU, which PDF rendering wants), a 300-second timeout as the backstop above the 240-second budget, both layers, and a BEDROCK_READ_TIMEOUT_SECONDS of 120 — the shared client's 25-second default is right for Haiku parse turns and far too short for a full résumé generation.

Three environment variables exist purely to keep WeasyPrint happy in a read-only filesystem: FONTCONFIG_PATH=/opt/fonts, and XDG_CACHE_HOME/HOME pointed at /tmp, the only writable path in a Lambda. These are the sort of thing you discover by deploying, not by reading.

The IAM policy is the clearest statement of what the agent is allowed to be. DynamoDB Query/GetItem/PutItem but no delete and no entry writes — the agent is read-only over your career data; the only thing it writes is its own run record. S3 scoped to resumes/*, so it cannot touch uploads/*. And lambda:InvokeFunction on its own ARN, constructed with !Sub from the function name rather than !GetAtt — a self-referential GetAtt is a CloudFormation circular dependency and the stack won't deploy.

7. Tests — five new files, ~800 lines

Because agent.py is a pure function, test_resume_agent_loop.py can drive the entire six-phase loop against a faked bedrock_client — scripting a sequence of responses to assert that retrieval_done exits the loop, that the token ceiling raises, that stagnation stops revisions, that the duplicate nudge appears on the third identical call. That testability is the payoff for keeping I/O out of the brain, and it's the strongest structural argument in the slice.
